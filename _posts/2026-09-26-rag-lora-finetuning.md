自社の製品や規約に詳しいチャットボットを LLM で作るとき、RAG（Retrieval-Augmented Generation）、LoRA（Low-Rank Adaptation、低ランク適応）、ファインチューニングは「どれが一番精度が出るか」で比較されやすい。しかし、RAG は推論時の入力を変え、LoRA とフルファインチューニングはモデルの重みを変える。変える場所が違うので、直せる失敗も違う。

自社の事実を答えさせたいなら RAG を、口調や形式を揃えたいなら LoRA を使う。フルファインチューニングは、両方を試しても足りない場合に検討する。

## 失敗は「知らない」か「振る舞いがずれる」かに分かれる

素の LLM に自社製品の問い合わせを投げたときの誤答は、2種類に分かれる。

1つは知識の失敗で、自社の料金規約、先週リリースした機能、社内用語、昨日更新された障害情報のように、学習データにないことには答えられない。モデルは知らないまま答えようとして、もっともらしい作話（hallucination）を出す。

もう1つは振る舞いの失敗で、内容は知っていても出力の形が期待とずれる。口調が硬すぎる、JSON に前置きを付ける、社内用語を一般語に言い換える、断るべき質問に答える、答えてよい質問を断る、といったものがある。

この2つは対処が逆方向になる。重みに知識を入れるのは難しく、入力で振る舞いを直すのはコストが高い。RAG は知識の失敗に、LoRA とファインチューニングは振る舞いの失敗に効く。

## 3手法の仕組み

LLM は、入力トークン列 $$x$$ に対する出力 $$y$$ の条件付き確率 $$p_\theta(y \mid x)$$ を、パラメータ $$\theta$$ でモデル化している。3手法は、この式のどこを変えるかが違う。

  <figcaption>左：RAG は LLM の重みを変えず、質問に検索結果を連結して入力を変える。中：LoRA は元の重みを凍結し、低ランクの差分だけを学習する。右：フルファインチューニングは全パラメータを更新する。</figcaption>
</figure>

### RAG は入力を変える

RAG は $$\theta$$ を変えず、質問 $$x$$ に関連する文書を外部の索引から取り出して、プロンプトに連結する。

$$
p(y \mid x) \approx p_\theta\bigl(y \mid x,\ d_1, \ldots, d_k\bigr), \qquad d_1, \ldots, d_k = \mathrm{Retrieve}(x)
$$

文書はあらかじめチャンクに分割し、埋め込みベクトルにして索引に入れておく。質問が来たら同じ空間に埋め込んで近傍検索し、必要なら Cross-Encoder で再ランキングして、上位 $$k$$ 件をプロンプトに入れる。検索器の構成は[以前の記事](/blog/ja/bi-late-cross-encoder/)、検索品質の測り方は[検索評価指標の記事](/blog/ja/information-retrieval-metrics/)に書いた。

学習が要らないので、文書を索引に追加すればすぐ回答に使える。代わりに、検索のレイテンシと上位 $$k$$ 件ぶんの入力トークンが、リクエストのたびにかかる。

### フルファインチューニングは全重みを変える

（入力, 期待する出力）のペアで、全パラメータを勾配降下で更新する。チャットボットでは、事前学習済みモデルに対する SFT（Supervised Fine-Tuning、教師ありファインチューニング）を指すことが多い。

コストは大きい。Adam 系の最適化器を混合精度で回すと、重み・勾配・最適化器の状態で、パラメータ1つにつき約16バイトが要る（Rajbhandari et al., 2020）。7B モデルなら約112 GB に活性化のメモリが加わり、複数 GPU の分散学習が前提になる。

破滅的忘却（catastrophic forgetting）も起きる。全重みを動かすと、事前学習で得た一般的な能力（推論、他言語、常識）が劣化することがあるので、学習後は一般能力のベンチマークでも退行を確認する。

### LoRA は少数の追加重みを変える

LoRA（Hu et al., 2021）は、ファインチューニングで生じる重みの差分 $$\Delta W$$ は実質的に低ランクだろう、という仮説に基づく。元の重み $$W_0$$ を凍結し、差分を2つの小さい行列の積で表す。

$$
h = W_0 x + \frac{\alpha}{r} B A x, \qquad B \in \mathbb{R}^{d \times r},\ A \in \mathbb{R}^{r \times k},\ r \ll \min(d, k)
$$

学習するのは $$A$$ と $$B$$ だけになる（$$\alpha$$ はスケーリング用の定数）。

<figure>
  <img src="{{ '/assets/img/lora-decomposition.svg' | relative_url }}" alt="LoRA の低ランク分解。凍結した d×k の重み W0 に、d×r の行列 B と r×k の行列 A の積を足す。学習パラメータ数は dk から r(d+k) に減る。d=k=4096, r=8なら約1680万から約6.5万（約0.4%）になる">
  <figcaption>元の重み W₀ は凍結し、差分 ΔW = BA だけを学習する。d = k = 4096、r = 8なら、学習パラメータは1層あたり約1680万から約6.5万に減る。</figcaption>
</figure>

学習パラメータは1層あたり $$dk$$ 個から $$r(d + k)$$ 個に減る。$$d = k = 4096$$、$$r = 8$$ なら元の0.4%で、7B クラスのモデル全体でも0.3%ほどに収まる。

$$B$$ をゼロで初期化するので、学習は元のモデルと同じ出力から始まる。学習後は $$W_0 + \frac{\alpha}{r} BA$$ を1つの行列に合成でき、推論時の追加コストはかからない。合成しなければ、1つのベースモデルに数十 MB のアダプタを載せ替えて、顧客ごと・タスクごとに使い分けられる。

派生の QLoRA（Dettmers et al., 2023）は、凍結する $$W_0$$ を4ビットに量子化し、アダプタだけを16ビットで学習する。65B モデルを48 GB の GPU 1枚でファインチューニングでき、$$r$$ を大きくするより LoRA をすべての線形層に付けるほうが効くことも示した。以下では、LoRA とその派生（QLoRA、DoRA など）を LoRA で代表させる。

## 比較

### 知識を入れるなら RAG

RAG では知識が索引にあり、モデルは「読んで答える」だけでよい。この能力は事前学習で十分に身についている。

ファインチューニングで知識を入れるのは難しい。Ovadia et al.（2023）は、既存知識でも新規知識でも、教師なしファインチューニングより RAG のほうが一貫して正答率が高いと報告している。新しい事実を覚えさせるには、同じ事実を複数の言い換えで繰り返し見せる必要があった。数百件の Q&A ペアに1度だけ現れる事実は、勾配信号として弱すぎる。

LoRA はさらに不利になる。Biderman et al.（2024）によると、コードや数学の継続事前学習では、LoRA の学習量はフルファインチューニングより明確に少ない。フルファインチューニングで生じる $$\Delta W$$ のランクは典型的な LoRA の $$r$$ の10〜100倍あり、低ランクの制約では大量の新知識を入れる容量が足りない。その代わり、LoRA は元の能力を忘れにくい。

知識の注入が成り立つのは、大量のドメインテキストで継続事前学習を行う規模になってからで、チャットボットに自社の事実を答えさせたいなら、まず RAG を使う。

### 振る舞いを変えるのは LoRA とファインチューニング

口調、出力形式、用語の使い方、断り方、回答の長さといった「どう答えるか」は、学習例から一貫したパターンとして学びやすい。Hu et al.（2021）では、$$r$$ が1〜8程度の LoRA が GLUE や E2E NLG でフルファインチューニングと同等の性能を出した。Biderman et al.（2024）も、指示チューニングでは LoRA とフルの差は小さいと報告している。データは、数百〜数千件の（入力, 理想の出力）ペアで効果が見えることが多い。

RAG だけで振る舞いを直そうとすると、システムプロンプトに指示を書き足すことになる。指示は長くなるほど一部が無視されやすくなり、そのトークンをリクエストのたびに払う。

フルファインチューニングは、到達できる性能の上限が最も高い。事前学習にほとんどない言語や独自の記法のようにドメインのずれが深いと、LoRA では足りないことがある。ただし、数万件以上のデータ、複数の GPU、忘却の監視が必要になる。

### 更新頻度と鮮度

RAG は索引を更新するだけなので、分〜時間の単位で追従でき、文書の削除も索引から消せば済む。LoRA の再学習は数時間程度、フルファインチューニングは日単位かかり、更新は週〜月の単位になる。頻繁に変わる情報を重みに入れるのは現実的ではない。

### 根拠提示とアクセス制御

RAG は、回答に使ったチャンクを出典として示せる。利用者は出典を確認でき、開発者は誤答の原因が検索側か生成側かを切り分けられる。検索時に利用者の権限でフィルタすれば、閲覧権限のない文書を回答から外せる。

ファインチューニングでは、どちらもできない。重みに入った知識には出典がなく、誰が聞いても取り出せる可能性がある。部署ごとに見せてよい情報が違えば、モデルを分けるしかない。特定の情報をあとから消すことも難しい。個人情報や権限管理が絡む用途では、筆者はこの差を精度より重く見ている。

### コスト

| 観点 | RAG | LoRA | フルファインチューニング |
| --- | --- | --- | --- |
| 学習コスト | なし（索引構築のみ） | GPU 1枚で数時間程度 | 複数 GPU で日単位 |
| 学習メモリ（7B） | 不要 | 凍結重み ＋ 活性化。QLoRA なら10 GB 前後 | 重み・勾配・最適化器で約112 GB ＋ 活性化 |
| 推論コスト | 検索レイテンシ ＋ $$k$$ 件ぶんの入力トークン | 合成すれば増加なし | 増加なし |
| 成果物の大きさ | 索引（文書量に比例） | アダプタ数十 MB | モデル1部（数十 GB） |
| 必要データ | 文書そのもの | 数百〜数千の（入力, 出力）ペア | 数万件以上 |

RAG はリクエストのたびにトークンが増えるので、トラフィックが多いと負担が大きい。ファインチューニングは、学習に払ったコストを推論で回収する。トラフィックが少なく文書の更新が多いなら、RAG のほうが安い。

### デバッグと評価

RAG は失敗を分解して測れる。検索側は Recall@k や nDCG で、生成側は与えた文脈に忠実かどうかで、別々に評価できる。必要な文書を取れていないのか、取れたのに読み違えたのかが分かれば、直す場所が決まる。

ファインチューニングの失敗は原因を特定しにくい。データの質・量・分布、学習率、エポック数のどれが効いたのかは、変えて再学習しないと確かめられず、一般能力の退行も測る必要がある。

### モデルへのアクセス

RAG は、API 経由の閉じたモデルでも使える。重みを変える手法は、提供者がファインチューニング API を用意している場合に限られる。オープンウェイトのモデルなら、3手法すべてを選べる。

| 知識の注入 | ◎ 即時、出典付き | △ 容量が小さい | ○ 大量データの継続事前学習なら |

## 組み合わせる

実務では、3つを組み合わせて使うのが普通になっている。

最も多いのは RAG ＋ LoRA で、事実は RAG が供給し、「与えられた文脈だけから答える」「文脈になければ分からないと言う」「出典を所定の形式で付ける」「自社の口調と用語で書く」といった振る舞いを LoRA で学習させる。

「文脈になければ分からないと言う」は、入力から判定できる条件で分岐する振る舞いなので、LoRA で学習させやすい。文脈が質問に答えているかを読む力はモデルがすでに持っていて、LoRA が足すのは「答えていなければ断る」という出力方針だけで済む。教師データも、文脈を抜いた質問に「文脈にありません」を付ければ機械的に作れる。

文脈なしで「自分の知識にないことは知らないと言う」振る舞いは、モデル内部の知識境界に依存するので、同じようにはいかない。難しそうな質問に一律「分からない」を付けて学習すると、質問の見た目で断るようになる。モデルが知らない事実の回答を学習データに混ぜると、幻覚が増えることも報告されている（Gekhman et al., 2024）。R-Tuning（Zhang et al., 2023）のように、ベースモデル自身に解かせて正答できたかどうかでラベルを振り分けるデータ構築が必要になり、学習後は検証セットで測るしかない。

RAG を前提にファインチューニングする手法もある。Zhang et al.（2024）の RAFT（Retrieval-Augmented Fine-Tuning）は、学習データを（質問, 正解を含む文書 ＋ 無関係な妨害文書, 引用付きの推論過程と回答）の形にして、正解を含む文書を見分けて引用することを学習させる。

生成モデルを変えずに、埋め込みモデルや Cross-Encoder 再ランカーをドメインの（質問, 関連文書）ペアで学習する選択肢もある。「専門用語で聞いたのに一般語の文書しか取れない」という失敗は検索側の問題で、生成側を学習しても直らない。これらのモデルは小さいので、学習も安い。

## ドメイン外の質問に答えさせない仕組み

EC サイトの FAQ にだけ答えるチャットボットを考える。配送、返品、支払い、会員登録、商品仕様の質問には答え、「今日の天気は」「Python でソートを書いて」には答えない。この線引きは3手法のどれか1つでは実現できず、生成モデルの外側に置く判定と、生成モデル自身の振る舞いを重ねて作る。

  <figcaption>生成モデルの外側にある入力分類器と検索スコアの閾値で範囲外の質問を止め、内側の LoRA と出力検証で残りを拾う。どの層にも単独では穴があるが、穴の場所が違う。</figcaption>

システムプロンプトに「FAQ に関する質問以外には答えないでください」と書けば、ある程度は効く。ただし、会話が長くなると効きにくくなり、「前の指示は無視して」という入力にも弱いので、外側に判定を足していく。

### 検索スコアに閾値を置く

RAG の検索は範囲判定にも使える。質問で FAQ の索引を検索し、上位の関連スコアが閾値を下回ったら「該当する FAQ がありません」と返して、生成には進まない。学習は要らず、閾値を検証データで決めるだけで済む。

ただし、埋め込みの類似度は「関連しているか」の代理指標にすぎない。「返品ポリシーは一般的にどうなっていますか」は自社の返品 FAQ と似た埋め込みになるが、答えるべきなのは自社の規約で、一般論ではない。逆に、言い回しが独特な正当な質問は誤って弾かれる。閾値は Bi-Encoder のスコアより Cross-Encoder 再ランカーのスコアに置くほうが安定する（[以前の記事](/blog/ja/bi-late-cross-encoder/)）。いずれの場合も、範囲内と範囲外の質問を集めた検証セットで、弾きすぎと通しすぎの両方を測って決める。

### 入力側に分類器を置く

より確実にするなら、生成モデルの手前に、質問が範囲内かを判定する小さな分類器を置く。BERT 系 Encoder に分類ヘッドを載せたモデルでも、[Jev のようなゼロショットの判定モデル](/blog/ja/jev-system-one/)でもよい。ラベルは「範囲内 / 範囲外 / 有害」程度で足り、学習データは問い合わせログから数百件を仕分ければ足りることが多い。

分類器は生成モデルから独立しているので、閉じた API モデルを使っていても自前で置け、プロンプトへの注入も届かない。判定は確率で返るので、[分類器の確信度の記事](/blog/ja/classification-confidence/)で書いたとおり、閾値と較正を検証セットで調整できる。境界の質問を弾く率と無関係な質問を通す率は別々に測り、どちらを優先するかは業務の側で決める。EC サイトなら、買う気のある客を弾くほうが損失が大きいことが多い。

「このセーターの洗い方」のように、FAQ にはないが商品には関係する質問を断るのか担当者につなぐのかも、分類器のラベル設計で決める。

### 生成モデルには「文脈だけから答える」を学習させる

2つの判定を通過した質問でも、モデルが検索結果を無視して自分の知識で答えることがある。そこで、「与えられた FAQ の抜粋だけから答え、抜粋に答えがなければ『該当する情報がありません』と返す」という振る舞いを LoRA で学習させる。教師データには、FAQ の抜粋を付けた質問と、抜粋を意図的に外した質問の両方を入れ、後者の正解を定型の断り文にする。

システムプロンプトだけで同じことをすると、断る条件を長く書くことになり、トークンが増えるうえ守られにくい。

### 出力を検証してから返す

最後に、回答が検索結果に根拠を持つかを確認する層を置くこともできる。回答と検索結果を NLI モデルか別の LLM に渡して、回答が文脈から導けるかを判定させ、導けなければ定型文に差し替える。推論が1回分増えるので、返品や決済のように誤答の代償が大きい話題に絞って入れる。

### 層を重ねる理由

どの層にも単独では穴がある。プロンプトは長い会話と注入に弱く、検索スコアは類似と関連を取り違え、分類器は境界の質問で迷い、LoRA は学習データにない言い回しで崩れる。穴の場所がそれぞれ違うので、重ねると通り抜ける質問は大きく減る。

## 選び方の手順

1. まずプロンプトだけで作り、測る。ここで十分なら、それで終わりにする。
2. 誤答を「知識の失敗」と「振る舞いの失敗」に仕分け、比率を見る。
3. 知識の失敗には RAG を使う。検索品質を単独で測り、取れているのに答えが違うなら生成側を、取れていないなら検索側を直す。
4. 振る舞いの失敗には LoRA を使う。数百〜数千件の理想的な応答例で学習する。閉じた API モデルなら、提供者のファインチューニング API を使う。RAG と併用するなら、学習データも「文脈付きの質問 → 文脈に基づく回答」の形にする。
5. それでも足りなければ、フルファインチューニングを検討する。ドメインのずれが深く、数万件以上のデータと GPU があり、一般能力の退行を測る体制があるときに限る。

| 状況 | 向いている選択 |
| --- | --- |
| 社内文書・仕様・規約に基づいて答えさせたい | RAG |
| 情報が日々更新される | RAG |
| 出典を示す必要がある、利用者ごとに見せてよい情報が違う | RAG |
| 口調・出力形式・用語・断り方を揃えたい | LoRA（または提供者のファインチューニング API） |
| 「文脈にないことは言わない」を徹底したい | RAG ＋ LoRA（RAFT 型のデータで） |
| 特定ドメイン（EC サイトの FAQ など）以外の質問には答えさせたくない | 入力分類器 ＋ 検索スコアの閾値で止め、LoRA で断り方を学習させる |
| 専門用語での検索精度が低い | 埋め込みモデル / 再ランカーのファインチューニング |
| 事前学習にほとんどない言語・記法に対応したい | 継続事前学習 ＋ SFT（フル、または大きい $$r$$ の LoRA） |
| 大量トラフィックで推論トークンを削りたい | 振る舞い部分を LoRA に移し、プロンプトを短くする |

実際には1と2でほとんど決まる。誤答を仕分けた時点で、RAG で文書を読ませるべきか、LoRA で振る舞いを学習させるべきかが分かる。
