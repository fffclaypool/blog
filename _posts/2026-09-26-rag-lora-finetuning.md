自社の製品や規約に詳しいチャットボットを LLM で作ろうとすると、RAG（Retrieval-Augmented Generation）、LoRA（Low-Rank Adaptation、低ランク適応）、ファインチューニングの3つが候補に挙がり、「どれが一番精度が出るか」で比較されることが多い。しかし、この3つは同じ問題を解く代替手段ではない。RAG は推論時の入力を変え、LoRA とフルファインチューニングはモデルの重みを変える。変える場所が違うので、直せる失敗も違う。

そのため、自社の事実を答えさせたいなら RAG を、口調や形式を揃えたいなら LoRA を使う。フルファインチューニングは、その両方を試しても足りないと分かってから検討すればよい。

## 失敗は「知らない」か「ふるまいがずれる」かに分かれる

素の LLM に自社製品の問い合わせを投げると、誤答は大きく2種類に分かれる。

1つは知識の失敗で、学習データに含まれていないことには答えられない。自社の料金規約、先週リリースした機能、社内でしか通じない用語、昨日更新された障害情報などがこれにあたる。モデルは知らないまま答えようとするので、もっともらしい作話（hallucination）が出てくる。

もう1つはふるまいの失敗で、内容は知っていても出力の形が期待とずれる。口調が硬すぎる、JSON で返してほしいのに前置きを付ける、社内用語を一般語に言い換える、答えるべきでない質問に答える、答えてよい質問を断る、といった失敗がこれにあたる。

この2つは対処が逆方向になるので、分けて考える。重みに知識を入れるのは難しく、入力でふるまいを直すのはコストが高い。RAG は知識の失敗に、LoRA とファインチューニングはふるまいの失敗に効く。

## 3手法の仕組み

LLM は、入力トークン列 $$x$$ に対する出力 $$y$$ の条件付き確率 $$p_\theta(y \mid x)$$ を、パラメータ $$\theta$$ でモデル化している。3手法の違いは、この式のどこを変えるかで整理できる。

  <figcaption>左：RAG は LLM の重みを変えず、質問に検索結果を連結して入力を変える。中：LoRA は元の重みを凍結し、低ランクの差分だけを学習する。右：フルファインチューニングは全パラメータを更新する。</figcaption>
</figure>

### RAG は入力を変える

RAG は $$\theta$$ を変えない。質問 $$x$$ に関連する文書を外部の索引から取り出し、プロンプトに連結して LLM に渡す。

$$
p(y \mid x) \approx p_\theta\bigl(y \mid x,\ d_1, \ldots, d_k\bigr), \qquad d_1, \ldots, d_k = \mathrm{Retrieve}(x)
$$

事前に、文書をチャンクに分割して埋め込みベクトルにし、索引に入れておく。質問が来たら同じ空間に埋め込んで近傍検索し、必要なら Cross-Encoder で再ランキングして、上位 $$k$$ 件をプロンプトに入れて生成する。検索器の構成（Bi-Encoder / Late Interaction / Cross-Encoder）は[以前の記事](/blog/ja/bi-late-cross-encoder/)で、検索品質の測り方は[検索評価指標の記事](/blog/ja/information-retrieval-metrics/)で書いた。

LLM 側では何も学習しないので、文書を索引に追加すればすぐ回答に使える。その代わり、検索のレイテンシと上位 $$k$$ 件ぶんの入力トークンが、リクエストのたびにかかる。

### フルファインチューニングは全重みを変える

（入力, 期待する出力）のペアを用意し、全パラメータを勾配降下で更新する。チャットボットの文脈では、事前学習済みモデルに対する SFT（Supervised Fine-Tuning、教師ありファインチューニング）を指すことが多い。

まずコストが大きい。Adam 系の最適化器を混合精度で回すと、重み・勾配・最適化器の状態を合わせて、パラメータ1つにつき約16バイトが要る（Rajbhandari et al., 2020）。7B モデルなら約112 GB になり、さらに活性化のメモリが加わる。単一 GPU には載らないので、複数 GPU の分散学習が前提になる。

破滅的忘却（catastrophic forgetting）も起きる。自社データで全重みを動かすと、事前学習で獲得した一般的な能力（推論、他言語、常識）が劣化することがある。そのため、ファインチューニング後は目的タスクの精度に加えて、一般能力のベンチマークで退行がないかも確認する。

### LoRA は少数の追加重みを変える

LoRA（Hu et al., 2021）は、ファインチューニングで生じる重みの差分 $$\Delta W$$ は実質的に低ランクだろう、という仮説から出発している。元の重み $$W_0$$ は凍結し、差分を2つの小さい行列の積で表す。

$$
h = W_0 x + \frac{\alpha}{r} B A x, \qquad B \in \mathbb{R}^{d \times r},\ A \in \mathbb{R}^{r \times k},\ r \ll \min(d, k)
$$

学習するのは $$A$$ と $$B$$ だけになる（$$\alpha$$ はスケーリング用の定数）。

<figure>
  <img src="{{ '/assets/img/lora-decomposition.svg' | relative_url }}" alt="LoRA の低ランク分解。凍結した d×k の重み W0 に、d×r の行列 B と r×k の行列 A の積を足す。学習パラメータ数は dk から r(d+k) に減る。d=k=4096, r=8なら約1680万から約6.5万（約0.4%）になる">
  <figcaption>元の重み W₀ は凍結し、差分 ΔW = BA だけを学習する。d = k = 4096、r = 8なら、学習パラメータは1層あたり約1680万から約6.5万に減る。</figcaption>
</figure>

学習パラメータは1層あたり $$dk$$ 個から $$r(d + k)$$ 個に減る。$$d = k = 4096$$、$$r = 8$$ なら元の0.4%で、7B クラスのモデル全体でも0.3%ほどに収まる。メモリの大半は凍結した重みと活性化が占める。

$$B$$ をゼロで初期化するので、学習は元のモデルと同じ出力から始まる。学習後は $$W_0 + \frac{\alpha}{r} BA$$ を1つの行列に合成でき、推論時の追加コストはかからない。合成しない場合は、1つのベースモデルに複数のアダプタ（数十 MB 程度）を載せ替えて使える。顧客ごと・タスクごとにアダプタを分けても、ベースの重みは1部で済む。

派生に QLoRA（Dettmers et al., 2023）がある。凍結する $$W_0$$ を4ビットに量子化してメモリに載せ、LoRA のアダプタだけを16ビットで学習する方法で、65B モデルを48 GB の GPU 1枚でファインチューニングできることを示した。同じ論文は、$$r$$ を大きくするより、LoRA をすべての線形層に付けるほうが効くとも報告している。

「低ランク学習」と呼ばれる手法は、LoRA とその派生（QLoRA、DoRA など）を指すと考えてよい。以下では LoRA で代表させる。

## 比較

### 知識を入れるなら RAG

RAG では知識が索引にあり、文書を1件追加すればすぐ回答に使える。モデルに求められるのは「読んで答える」ことだけで、この能力は事前学習で十分に身についている。

ファインチューニングで知識を入れるのは難しい。Ovadia et al.（2023）は、既存知識と新規知識の両方で、教師なしファインチューニングより RAG のほうが一貫して正答率が高いと報告している。同じ実験では、ファインチューニングで新しい事実を覚えさせるには、同じ事実を複数の言い換えで繰り返し見せる必要があることも分かった。事前学習では、1つの事実がウェブ上で何百通りもの表現で現れる。数百件の Q&A ペアに1度だけ現れる事実は、勾配信号として弱すぎる。

LoRA はさらに不利になる。Biderman et al.（2024）は、コードや数学のドメインで継続事前学習を行い、LoRA の学習量がフルファインチューニングより明確に少ないことを示した。フルファインチューニングで生じる $$\Delta W$$ のランクは、典型的な LoRA の $$r$$ の10〜100倍あった。低ランクの制約では、大量の新知識を入れるには容量が足りない。一方で同じ論文は、LoRA は元の能力を忘れにくいとも報告している。学習量が少ないぶん、忘却も少なくなる。

ファインチューニングで知識を入れる方法は、数百件の Q&A の規模では機能せず、大量のドメインテキストで継続事前学習を行う規模で初めて成り立つ。チャットボットに自社の事実を答えさせたいなら、まず RAG を使う。

### ふるまいを変えるのは LoRA とファインチューニング

口調、出力形式、専門用語の使い方、断り方の方針、回答の長さといった「どう答えるか」は、学習例から一貫したパターンとして学びやすい。Hu et al.（2021）の原論文でも、$$r$$ が1〜8程度の LoRA が、GLUE や E2E NLG でフルファインチューニングと同等の性能を出している。Biderman et al.（2024）も、継続事前学習では差が大きい一方、指示チューニングでは LoRA とフルの差は小さいと報告している。データも、数百〜数千件の（入力, 理想の出力）ペアで効果が見えることが多い。

RAG だけでふるまいを直そうとすると、システムプロンプトに指示を書き足していくことになる。短い指示なら十分に効くが、長くなるほど一部が無視されやすくなり、そのトークンをリクエストのたびに払う。few-shot 例を入れればさらに長くなる。冒頭で「入力でふるまいを直すのはコストが高い」と書いたのは、このことを指している。

フルファインチューニングは、到達できる性能の上限が最も高い。事前学習にほとんど含まれない言語、独自の記法やコード、モデルの応答分布そのものを変えたい場合など、ドメインのずれが深いと LoRA では足りないことがある。ただし、数万件以上のデータ、複数の GPU、忘却の監視が必要になる。

### 更新頻度と鮮度

RAG は索引を更新するだけなので、分〜時間の単位で追従できる。文書の削除も、索引から消せば済む。LoRA は再学習に数時間程度、フルファインチューニングは日単位の時間とコストがかかるため、更新は週〜月の単位になる。頻繁に変わる情報を重みに入れると、更新のたびに学習パイプラインを回すことになり、現実的ではない。

### 根拠提示とアクセス制御

RAG は、回答に使ったチャンクを出典として提示できる。利用者は出典を確認でき、開発者は誤答の原因が検索側か生成側かを切り分けられる。検索時に利用者の権限でフィルタをかければ、閲覧権限のない文書を回答から確実に外せる。

ファインチューニングでは、どちらもできない。重みに入った知識には出典がなく、誰がどのプロンプトで聞いても取り出せる可能性がある。部署ごとに見せてよい情報が違う場合は、モデルを部署ごとに分けるしかない。特定の情報をあとから消すことも難しい（機械的な「忘却」は未解決の問題として残っている）。個人情報や権限管理が絡む用途では、筆者はこの差を精度より重く見ている。

### コスト

| 観点 | RAG | LoRA | フルファインチューニング |
| --- | --- | --- | --- |
| 学習コスト | なし（索引構築のみ） | GPU 1枚で数時間程度 | 複数 GPU で日単位 |
| 学習メモリ（7B） | 不要 | 凍結重み ＋ 活性化。QLoRA なら10 GB 前後 | 重み・勾配・最適化器で約112 GB ＋ 活性化 |
| 推論コスト | 検索レイテンシ ＋ $$k$$ 件ぶんの入力トークン | 合成すれば増加なし | 増加なし |
| 成果物の大きさ | 索引（文書量に比例） | アダプタ数十 MB | モデル1部（数十 GB） |
| 必要データ | 文書そのもの | 数百〜数千の（入力, 出力）ペア | 数万件以上 |

推論コストの優劣は用途で変わる。RAG はリクエストのたびにトークンが増えるので、トラフィックが多いと負担が大きい。ファインチューニングは、学習に払ったコストを推論で回収する。トラフィックが少なく、文書の更新が多いなら、RAG のほうが安く済む。

### デバッグと評価

RAG は、失敗を分解して測れる。検索側は Recall@k や nDCG のような検索指標で、生成側は「与えた文脈に忠実か」で、別々に評価できる。誤答の原因が「必要な文書を取れていない」のか「取れたのに読み違えた」のかが分かれば、直す場所も決まる。

ファインチューニングの失敗は、原因を局所化しにくい。データの質・量・分布、学習率、エポック数のどれが効いたのかは、変えて再学習しないと確かめられない。加えて、一般能力の退行も測る必要がある。

### モデルへのアクセス

API 経由の閉じたモデルでも、RAG はいつでも使える。重みを変える手法は、提供者がファインチューニング API を用意している場合に限られる（内部で LoRA 相当を使っているかは、通常公開されない）。オープンウェイトのモデルなら、3手法すべてを選べる。

### 一覧

| 観点 | RAG | LoRA | フルファインチューニング |
| --- | --- | --- | --- |
| 変えるもの | 入力 | 少数の追加重み | 全重み |
| 知識の注入 | ◎ 即時、出典付き | △ 容量が小さい | ○ 大量データの継続事前学習なら |
| ふるまいの変更 | △ プロンプトで毎回指示 | ○ 数百〜数千件で効く | ◎ 天井が最も高い |
| 更新の速さ | 分〜時間 | 時間〜日 | 日〜週 |
| 出典の提示 | 可 | 不可 | 不可 |
| 利用者ごとの権限制御 | 検索時にフィルタ | モデルを分ける | モデルを分ける |
| 忘却のリスク | なし | 小 | 大 |
| 閉じた API モデルで | 可 | 提供者次第 | 提供者次第 |

## 組み合わせる

実務では3つから1つを選ぶのではなく、組み合わせて使うのが普通になっている。

最も多いのは RAG ＋ LoRA の組み合わせで、事実は RAG が供給し、LoRA はふるまいを担う。具体的には、「与えられた文脈だけから答える」「文脈になければ分からないと言う」「出典を所定の形式で付ける」「自社の口調と用語で書く」といったふるまいを LoRA で学習させる。それぞれが得意な失敗を直すので、役割が重ならない。

「文脈になければ分からないと言う」は、入力から判定できる条件で分岐するふるまいなので、LoRA で学習させやすい。文脈が質問に答えているかを読む力は事前学習済みモデルがすでに持っていて、LoRA が足すのは「答えていなければ断る」という出力方針だけで済む。教師データも、文脈を抜いた質問に「文脈にありません」を付けるだけで機械的に作れる。

一方、文脈なしで「自分の知識にないことは知らないと言う」ふるまいは、モデル内部の知識境界に依存するので、同じようにはいかない。難しそうな質問に一律「分からない」を付けて学習すると、質問の見た目で断るようになる。モデルが知らない事実の回答を学習データに混ぜると、知らなくてもそれらしく答えるパターンを学び、幻覚が増えることも報告されている（Gekhman et al., 2024）。R-Tuning（Zhang et al., 2023）のように、まずベースモデル自身に解かせ、正答できたかどうかでラベルを振り分けるデータ構築が必要になる。これは LoRA かフルかに関係なく難しい問題で、較正と同じく、学習後に検証セットで測るしかない。

RAG を前提にファインチューニングする手法もある。Zhang et al.（2024）はこれを RAFT（Retrieval-Augmented Fine-Tuning）と名付けた。学習データを（質問, 正解を含む文書 ＋ 無関係な妨害文書, 引用付きの推論過程と回答）の形にして、複数の検索結果から正解を含むものを見分け、妨害文書を無視して引用することをモデルに学習させる。検索器が完璧でないことを前提に、生成側をそれに合わせる考え方をとっている。

生成モデルを変えない選択肢もある。埋め込みモデルや Cross-Encoder 再ランカーを、ドメインの（質問, 関連文書）ペアで学習する。「専門用語で聞いたのに一般語の文書しか取れない」という失敗は検索側の問題なので、生成側をいくら学習しても直らない。これらのモデルは小さいぶん学習も安く、投資対効果が高いことが多い。

## ドメイン外の質問に答えさせない仕組み

EC サイトの FAQ にだけ答えるチャットボットを考える。配送、返品、支払い、会員登録、商品仕様に関する質問には答え、「今日の天気は」「Python でソートを書いて」のような無関係な質問には答えない。この線引きは、3手法のどれか1つでは実現できない。生成モデルの外側に置く判定と、生成モデル自身のふるまいを重ねて作る。

最も手軽な方法は、システムプロンプトに「FAQ に関する質問以外には答えないでください」と書くことで、ある程度は効く。ただし、会話が長くなると指示が効きにくくなり、「前の指示は無視して」という入力にも弱い。プロンプトは最初の1層と考え、外側に判定を足していく。

### 検索スコアに閾値を置く

RAG の検索は、そのまま範囲判定にも使える。質問で FAQ の索引を検索し、上位の関連スコアが閾値を下回ったら「該当する FAQ がありません」と返して、生成には進まない。天気の質問は FAQ のどの項目とも似ていないので、ここで止まる。学習は要らず、閾値を検証データで決めるだけで済む。

この方法には弱点もある。埋め込みの類似度は「関連しているか」の代理指標にすぎない。「返品ポリシーは一般的にどうなっていますか」という質問は自社の返品 FAQ と似た埋め込みになるが、答えるべきなのは自社の規約で、一般論ではない。逆に、言い回しが独特な正当な質問はスコアが伸びず、誤って弾かれる。閾値は、Bi-Encoder のスコアより Cross-Encoder 再ランカーのスコアに置くほうが安定する（[以前の記事](/blog/ja/bi-late-cross-encoder/)）。どちらの場合も、範囲内の質問と範囲外の質問を集めた検証セットで、弾きすぎと通しすぎの両方を測って閾値を決める。

### 入力側に分類器を置く

より確実にするなら、生成モデルの手前に「この質問は範囲内か」を判定する小さな分類器を置く。BERT 系 Encoder に分類ヘッドを載せたモデルでも、[Jev のようなゼロショットの判定モデル](/blog/ja/jev-system-one/)でも使える。ラベルは「範囲内 / 範囲外 / 有害」程度で足りる。学習データは（質問, ラベル）のペアだけなので、回答例を書くよりずっと安く集まる。実際の問い合わせログから数百件を仕分ければ足りることが多い。

分類器は生成モデルから独立している。そのため、閉じた API モデルを使っていても自前で置けるし、プロンプトへの注入も届かない。判定は確率で返るので、[分類器の確信度の記事](/blog/ja/classification-confidence/)で書いたとおり、閾値と較正を検証セットで調整できる。「ボタンが押せない」のような境界の質問を弾く率と、無関係な質問を通す率を別々に測り、どちらを優先するかは業務の側で決める。EC サイトなら、買う気のある客を弾くほうが損失が大きいことが多い。

境界の設計もここで決まる。「このセーターの洗い方」は FAQ にはないが、商品には関係する。こうした質問を範囲外として断るのか、担当者につなぐのかは、分類器のラベル設計で決めることで、生成モデルの側では決まらない。

### 生成モデルには「文脈だけから答える」を学習させる

2つの判定を通過した質問だけが生成モデルに届く。それでも、モデルが検索結果を無視して自分の知識で答えることがある。ここで、前節の RAG ＋ LoRA を使う。「与えられた FAQ の抜粋だけから答え、抜粋に答えがなければ『該当する情報がありません』と返す」というふるまいを LoRA で学習させる。教師データとして、FAQ の抜粋を付けた質問と、抜粋を意図的に外した質問の両方を作る。抜粋を外した質問の正解は、定型の断り文になる。前節で書いたとおり、これは入力から判定できる条件なので、LoRA で安定して学べる。

システムプロンプトだけで同じことをすると、断る条件を長く書くことになり、リクエストごとのトークンが増えるうえ、守られにくい。LoRA に移せば、プロンプトは短くて済む。

### 出力を検証してから返す

最後に、生成した回答が検索結果に根拠を持つかを確認する層を置くこともできる。回答と検索結果のペアを NLI モデルか別の LLM に渡し、「回答は文脈から導けるか」を判定させる。導けなければ回答を捨てて、定型文に差し替える。生成モデルが一般知識で答えてしまった場合も、ここで止められる。推論が1回分増えるので、返品や決済のように誤答の代償が大きい話題に絞って入れる。

### 層を重ねる理由

どの層にも単独では穴がある。プロンプトは長い会話と注入に弱く、検索スコアは類似と関連を取り違え、分類器は境界の質問で迷い、LoRA は学習データにない言い回しで崩れる。ただし穴の場所がそれぞれ違うので、重ねると通り抜ける質問は大きく減る。EC サイトの FAQ ボットなら、入力分類器と検索スコアの閾値で範囲外を止め、LoRA で「文脈にないことは言わない」を学習させ、出力検証は誤答が高くつく話題に絞る構成が現実的だと考えている。

## 選び方の手順

1. まずプロンプトだけで作り、測る。システムプロンプトと few-shot 例でどこまで到達できるかを確認する。ここで十分なら、それで終わりにする。
2. 誤答を「知識の失敗」と「ふるまいの失敗」に仕分ける。混ざっているのが普通なので、比率を見る。
3. 知識の失敗には RAG を使う。索引を作り、検索品質を単独で測る。取れているのに答えが違うなら生成側を、取れていないなら検索側を直す。
4. ふるまいの失敗には LoRA を使う。数百〜数千件の理想的な応答例を用意して学習する。閉じた API モデルなら、提供者のファインチューニング API を使う。RAG と併用するなら、学習データも「文脈付きの質問 → 文脈に基づく回答」の形にする。
5. それでも足りなければ、フルファインチューニングを検討する。ドメインのずれが深く、数万件以上のデータと GPU があり、一般能力の退行を測る体制があるときに限る。

| 状況 | 向いている選択 |
| --- | --- |
| 社内文書・仕様・規約に基づいて答えさせたい | RAG |
| 情報が日々更新される | RAG |
| 出典を示す必要がある、利用者ごとに見せてよい情報が違う | RAG |
| 口調・出力形式・用語・断り方を揃えたい | LoRA（または提供者のファインチューニング API） |
| 「文脈にないことは言わない」を徹底したい | RAG ＋ LoRA（RAFT 型のデータで） |
| 特定ドメイン（EC サイトの FAQ など）以外の質問には答えさせたくない | 入力分類器 ＋ 検索スコアの閾値で止め、LoRA で断り方を学習させる |
| 専門用語での検索精度が低い | 埋め込みモデル / 再ランカーのファインチューニング |
| 事前学習にほとんどない言語・記法に対応したい | 継続事前学習 ＋ SFT（フル、または大きい $$r$$ の LoRA） |
| 大量トラフィックで推論トークンを削りたい | ふるまい部分を LoRA に移し、プロンプトを短くする |

手順は5つあるが、実際には1と2でほとんど決まる。誤答を仕分けた時点で、RAG で文書を読ませるべきか、LoRA でふるまいを学習させるべきかが分かる。フルファインチューニングは、その両方を試したあとで検討すればよい。
