自社の製品や規約に詳しいチャットボットを LLM で作りたい。そう言ったときにまず挙がるのが RAG（Retrieval-Augmented Generation）、LoRA（Low-Rank Adaptation、低ランク適応）、ファインチューニングの 3 つで、「どれが一番精度が出るか」という並べ方で比較されることが多い。ただ、この 3 つは同じ問題を解く代替手段ではない。RAG は推論時の入力を変え、LoRA とフルファインチューニングはモデルの重みを変える。変える場所が違えば、直せる失敗も違う。

先に結論を書くと、自社の事実を答えさせたいなら RAG、口調や形式を揃えたいなら LoRA。フルファインチューニングは、その両方をやっても足りないと分かってからでよい。

## 失敗は「知らない」か「ふるまいがずれる」かに分かれる

素の LLM に自社製品の問い合わせを投げてみると、外れ方は大きく 2 通りに分かれる。

ひとつは知識の失敗だ。学習データに含まれていないことは答えられない。自社の料金規約、先週リリースした機能、社内でしか通じない用語、昨日更新された障害情報。知らないまま答えようとするので、もっともらしい作話（hallucination）になる。

もうひとつはふるまいの失敗で、内容は知っていても出力の形が期待とずれる。口調が硬すぎる。JSON で返してほしいのに前置きを付ける。社内用語を一般語に言い換えてしまう。答えるべきでない質問に答え、逆に答えてよい質問を断る。

この 2 つを分けて考えるのは、対処が逆方向だからだ。重みに知識を入れるのは難しく、入力でふるまいを直すのは高くつく。RAG は前者に、LoRA とファインチューニングは後者に効く。

## 3 手法の仕組み

LLM がやっているのは、入力トークン列 $$x$$ に対する出力 $$y$$ の条件付き確率 $$p_\theta(y \mid x)$$ をパラメータ $$\theta$$ でモデル化することだ。3 手法の違いは、この式のどこに手を入れるかで書き分けられる。

  <figcaption>左：RAG は LLM の重みには触らず、質問に検索結果を連結して入力を変える。中：LoRA は元の重みを凍結し、低ランクの差分だけを学習する。右：フルファインチューニングは全パラメータを更新する。</figcaption>

### RAG は入力を変える

$$\theta$$ には一切触らない。代わりに、質問 $$x$$ に関連する文書を外部の索引から取り出し、プロンプトに連結して渡す。

$$
p(y \mid x) \approx p_\theta\bigl(y \mid x,\ d_1, \ldots, d_k\bigr), \qquad d_1, \ldots, d_k = \mathrm{Retrieve}(x)
$$

パイプラインとしては、まず文書をチャンクに分割して埋め込みベクトルにし、索引に入れておく。質問が来たら同じ空間に埋め込んで近傍検索し、必要なら Cross-Encoder で再ランキングして、上位 $$k$$ 件をプロンプトに詰めて生成する。検索器の構成（Bi-Encoder / Late Interaction / Cross-Encoder）は[以前の記事](/blog/ja/bi-late-cross-encoder/)で、検索品質の測り方は[検索評価指標の記事](/blog/ja/information-retrieval-metrics/)で書いた。

LLM 側で「学習」されるものは何もない。文書を索引に追加すれば、その瞬間から回答に使える。コストは推論時に払う。検索のレイテンシと、上位 $$k$$ 件ぶんの入力トークンが毎リクエスト乗る。

### フルファインチューニングは全重みを変える

（入力, 期待する出力）のペアを用意し、全パラメータを勾配降下で更新する。チャットボットの文脈では、事前学習済みモデルに対する SFT（Supervised Fine-Tuning、教師ありファインチューニング）を指すことが多い。

問題はコストだ。Adam 系の最適化器を混合精度で回すと、重み・勾配・最適化器の状態でパラメータ 1 つにつき約 16 バイトが要る（Rajbhandari et al., 2020）。7B モデルなら約 112 GB で、そこに活性化のメモリが乗る。単一 GPU には載らず、複数 GPU の分散学習が前提になる。

もう 1 つの問題は破滅的忘却（catastrophic forgetting）だ。自社データで全重みを動かすと、事前学習で獲得した一般的な能力（推論、他言語、常識）が劣化しうる。ファインチューニング後には、目的タスクの精度だけでなく、一般能力のベンチマークで退行がないかも確認する必要がある。

### LoRA は少数の追加重みを変える

LoRA（Hu et al., 2021）の出発点は、ファインチューニングで生じる重みの差分 $$\Delta W$$ は実質的に低ランクだろう、という仮説だ。そこで元の重み $$W_0$$ は凍結し、差分を 2 つの小さい行列の積で表す。

$$
h = W_0 x + \frac{\alpha}{r} B A x, \qquad B \in \mathbb{R}^{d \times r},\ A \in \mathbb{R}^{r \times k},\ r \ll \min(d, k)
$$

学習するのは $$A$$ と $$B$$ だけだ（$$\alpha$$ はスケーリング用の定数）。

<figure>
  <img src="{{ '/assets/img/lora-decomposition.svg' | relative_url }}" alt="LoRA の低ランク分解。凍結した d×k の重み W0 に、d×r の行列 B と r×k の行列 A の積を足す。学習パラメータ数は dk から r(d+k) に減る。d=k=4096, r=8 なら約 1680 万から約 6.5 万（約 0.4%）になる">
  <figcaption>元の重み W₀ は凍結し、差分 ΔW = BA だけを学習する。d = k = 4096、r = 8 なら、学習パラメータは 1 層あたり約 1680 万から約 6.5 万に減る。</figcaption>
</figure>

学習パラメータは 1 層あたり $$dk$$ 個から $$r(d + k)$$ 個に減る。$$d = k = 4096$$、$$r = 8$$ なら 0.4% で、7B クラスのモデル全体で見ても 0.3% ほどに収まる。メモリの大半は凍結した重みと活性化になる。

$$B$$ をゼロで初期化するので、学習は元のモデルとまったく同じ出力から始まる。学習後は $$W_0 + \frac{\alpha}{r} BA$$ を 1 つの行列に合成でき、推論時の追加コストはない。合成しなければ、1 つのベースモデルに複数のアダプタ（数十 MB 程度）を載せ替えて使える。顧客ごと・タスクごとにアダプタを分けても、ベースの重みは 1 部でよい。

派生として QLoRA（Dettmers et al., 2023）がある。凍結する $$W_0$$ を 4 ビットに量子化してメモリに載せ、LoRA のアダプタだけを 16 ビットで学習する。65B モデルを 48 GB の GPU 1 枚でファインチューニングできることを示した。同じ論文は、LoRA をすべての線形層に付けるほうが $$r$$ を大きくするより効くとも報告している。

「低ランク学習」と呼ばれているものは、この LoRA とその派生（QLoRA、DoRA など）だと考えてよい。以下では LoRA で代表させる。

## 比較

### 知識を入れるなら RAG

知識は索引にあり、文書を 1 件追加すればその瞬間から回答に使える。モデルは「読んで答える」だけでよく、これは事前学習で十分に獲得している能力だ。

ファインチューニングで知識を入れるのは、直感に反して難しい。Ovadia et al.（2023）は既存知識と新規知識の両方で、教師なしファインチューニングより RAG のほうが一貫して正答率が高いと報告している。同じ実験で、ファインチューニングでモデルに新しい事実を覚えさせるには、同じ事実を複数の言い換えで繰り返し見せる必要があることも分かった。事前学習では 1 つの事実がウェブ上の何百通りもの表現で現れる。数百件の Q&A ペアに 1 度だけ現れる事実では、勾配信号として弱すぎる。

LoRA はさらに不利になる。Biderman et al.（2024）はコードや数学のドメインで継続事前学習を行い、LoRA の学習量がフルファインチューニングより明確に少ないことを示した。フルファインチューニングで生じる $$\Delta W$$ のランクは、典型的な LoRA の $$r$$ の 10〜100 倍あったという。低ランクという制約は、大量の新知識を詰め込むには容量が足りない。ただし同じ論文は、LoRA は元の能力を忘れにくいとも報告している。学習量が少ないことと忘却が少ないことは表裏一体だ。

つまりファインチューニングで知識を入れるのは「数百件の Q&A」の規模では機能せず、大量のドメインテキストで継続事前学習を行う規模の話になる。チャットボットに自社の事実を答えさせたいなら、まず RAG である。

### ふるまいを変えるのは LoRA とファインチューニング

口調、出力形式、専門用語の使い方、断り方の方針、回答の長さ。こうした「どう答えるか」は、学習例から一貫したパターンとして学びやすい。Hu et al.（2021）の原論文でも、$$r$$ が 1〜8 程度の LoRA が GLUE や E2E NLG でフルファインチューニングと同等の性能を出している。Biderman et al.（2024）も、継続事前学習では差が大きい一方で、指示チューニングでは LoRA とフルの差は小さいと報告している。必要なデータも数百〜数千件の（入力, 理想の出力）ペアで効果が見えることが多い。

RAG だけでふるまいを直そうとすると、システムプロンプトに指示を書き連ねることになる。短い指示なら十分に効くが、長くなるほど一部が無視されやすく、毎リクエストそのトークンを払い続ける。few-shot 例を入れればさらに長くなる。「入力でふるまいを直すのは高くつく」というのはこの意味だ。

フルファインチューニングは天井が最も高い。事前学習にほとんど含まれない言語、独自の記法やコード、モデルの応答分布そのものを変えたい場合のように、ドメインのずれが深いと LoRA では足りないことがある。ただしそれには数万件以上のデータと複数 GPU、そして忘却の監視が要る。

### 更新頻度と鮮度

索引を更新するだけの RAG は、分〜時間の単位で追従できる。文書の削除も索引から消せばよい。LoRA は再学習に数時間程度、フルファインチューニングは日単位とコストがかかるため、更新は週〜月の単位になる。頻繁に変わる情報を重みに入れる設計は、更新のたびに学習パイプラインを回すことになり、現実的でない。

### 根拠提示とアクセス制御

RAG は、どのチャンクを使って答えたかを出典として提示できる。利用者はそれを確認でき、開発者は誤答の原因が検索側か生成側かを切り分けられる。検索時に利用者の権限でフィルタをかければ、閲覧権限のない文書を回答から確実に外せる。

ファインチューニングには、この 2 つがない。重みに入った知識は出典を持たず、誰がどのプロンプトで聞いても取り出せる可能性がある。部署ごとに見せてよい情報が違うなら、モデルを部署ごとに分けるしかない。特定の情報を後から消すことも難しい（機械的な「忘却」は未解決の問題である）。個人情報や権限管理が絡む用途では、筆者はこの差を精度より重く見ている。

### コスト

| 観点 | RAG | LoRA | フルファインチューニング |
| --- | --- | --- | --- |
| 学習コスト | なし（索引構築のみ） | GPU 1 枚で数時間程度 | 複数 GPU で日単位 |
| 学習メモリ（7B） | 不要 | 凍結重み ＋ 活性化。QLoRA なら 10 GB 前後 | 重み・勾配・最適化器で約 112 GB ＋ 活性化 |
| 推論コスト | 検索レイテンシ ＋ $$k$$ 件ぶんの入力トークン | 合成すれば増加なし | 増加なし |
| 成果物の大きさ | 索引（文書量に比例） | アダプタ数十 MB | モデル 1 部（数十 GB） |
| 必要データ | 文書そのもの | 数百〜数千の（入力, 出力）ペア | 数万件以上 |

推論コストの見方は用途で逆転する。RAG は毎リクエストにトークンを積むので、大量トラフィックでは重い。ファインチューニングは学習に払った分を推論で回収する。逆にトラフィックが少なく、文書更新が多いなら RAG が安い。

### デバッグと評価

失敗を分解して測れるのが RAG の強みだ。検索側は Recall@k や nDCG のような検索指標で、生成側は「与えた文脈に忠実か」で別々に評価できる。誤答の原因が「必要な文書を取れていない」のか「取れたのに読み違えた」のかが分かれば、直す場所も決まる。

ファインチューニングの失敗は端から端まで一体で、原因を局所化しにくい。データの質・量・分布、学習率、エポック数のどれが効いたのかは、変えて再学習して確かめるしかない。加えて一般能力の退行も測る必要がある。

### モデルへのアクセス

API 経由の閉じたモデルを使う場合、RAG はいつでも可能だ。重みを変える手法は、提供者がファインチューニング API を用意している場合に限られる（内部で LoRA 相当を使っているかは通常公開されない）。オープンウェイトのモデルなら 3 手法すべてが選べる。

### 一覧

| 観点 | RAG | LoRA | フルファインチューニング |
| --- | --- | --- | --- |
| 変えるもの | 入力 | 少数の追加重み | 全重み |
| 知識の注入 | ◎ 即時、出典付き | △ 容量が小さい | ○ 大量データの継続事前学習なら |
| ふるまいの変更 | △ プロンプトで毎回指示 | ○ 数百〜数千件で効く | ◎ 天井が最も高い |
| 更新の速さ | 分〜時間 | 時間〜日 | 日〜週 |
| 出典の提示 | 可 | 不可 | 不可 |
| 利用者ごとの権限制御 | 検索時にフィルタ | モデルを分ける | モデルを分ける |
| 忘却のリスク | なし | 小 | 大 |
| 閉じた API モデルで | 可 | 提供者次第 | 提供者次第 |

## 組み合わせる

実務では 3 択ではなく、組み合わせが標準になる。

いちばん多いのは RAG ＋ LoRA だ。事実は RAG が供給し、LoRA は「与えられた文脈だけから答える」「文脈になければ分からないと言う」「出典を所定の形式で付ける」「自社の口調と用語で書く」といったふるまいを担う。それぞれが得意な失敗を直すので、役割の重複がない。

「文脈になければ分からないと言う」を LoRA で躾けられるのは、それが入力から判定できる条件で分岐するふるまいだからだ。文脈が質問に答えているかを読む力は事前学習済みモデルがすでに持っており、LoRA が乗せるのは「答えていなければ断る」という出力方針だけで済む。教師データも、文脈を抜いた質問に「文脈にありません」を付けるだけで機械的に作れる。一方、文脈なしで「自分の知識にないことは知らないと言う」は、モデル内部の知識境界に依存するので同じようにはいかない。難しそうな質問に一律「分からない」を付けて学習すると、質問の見た目で断るようになる。モデルが知らない事実の回答を学習データに混ぜると、知らなくてもそれらしく答えるパターンを学んで幻覚が増えることも報告されている（Gekhman et al., 2024）。R-Tuning（Zhang et al., 2023）のように、まずベースモデル自身に解かせ、正答できたか否かでラベルを振り分けるデータ構築が要る。これは LoRA かフルかに関係なく難しい問題で、較正と同じく学習後に検証セットで測るしかない。

RAG 前提でファインチューニングする手法もある。Zhang et al.（2024）はこれを RAFT（Retrieval-Augmented Fine-Tuning）と名付けた。学習データは（質問, 正解を含む文書 ＋ 無関係な妨害文書, 引用付きの推論過程と回答）の形で、複数の検索結果から正解を含むものを見分け、妨害文書を無視して引用することをモデルに教える。検索器が完璧でないことを前提に、生成側をそれに合わせる発想だ。

生成モデルに触らない選択肢もある。埋め込みモデルや Cross-Encoder 再ランカーを、ドメインの（質問, 関連文書）ペアで学習するやり方だ。「専門用語で聞いたのに一般語の文書しか取れない」という失敗は検索側の問題で、生成側をいくら学習しても直らない。モデルが小さいぶん学習も安く、投資対効果が高いことが多い。

## ドメイン外の質問に答えさせない仕組み

EC サイトの FAQ にだけ答えるチャットボットを考える。配送、返品、支払い、会員登録、商品仕様。この範囲の質問には答え、「今日の天気は」「Python でソートを書いて」のような無関係な質問には答えない。この線引きは 3 手法のどれか 1 つで実現するものではなく、生成モデルの外側に置く判定と、生成モデル自身のふるまいを重ねて作る。

いちばん手軽なのは、システムプロンプトに「FAQ に関する質問以外には答えないでください」と書くことだ。ある程度は効く。ただしそれだけに頼ると、会話が長くなるにつれて指示が薄れるし、「前の指示は無視して」という入力にも弱い。プロンプトは最初の一層と考え、外側に判定を足していく。

### 検索スコアで門を作る

RAG にはもともと門番がいる。質問で FAQ の索引を検索し、上位の関連スコアが閾値を下回ったら「該当する FAQ がありません」と返して生成に進まない。天気の質問は FAQ のどの項目とも似ていないので、ここで止まる。学習は要らず、閾値を検証データで決めるだけでよい。

弱点は、埋め込みの類似度が「関連しているか」の代理指標でしかないことだ。「返品ポリシーは一般的にどうなっていますか」という質問は自社の返品 FAQ と似た埋め込みになるが、答えるべきは自社の規約であって一般論ではない。逆に、言い回しが独特な正当な質問はスコアが伸びず、誤って弾かれる。閾値は Bi-Encoder のスコアより Cross-Encoder 再ランカーのスコアのほうが安定する（[以前の記事](/blog/ja/bi-late-cross-encoder/)）。どちらにせよ閾値は、範囲内の質問と範囲外の質問を集めた検証セットで、弾きすぎと通しすぎの両方を測って決める。

### 入力側に分類器を置く

もう一段確実にするなら、生成モデルの手前に「この質問は範囲内か」を判定する小さな分類器を置く。BERT 系 Encoder に分類ヘッドを載せたモデルでも、[Jev のようなゼロショットの判定モデル](/blog/ja/jev-system-one/)でもよい。ラベルは「範囲内 / 範囲外 / 有害」程度で済む。学習データは（質問, ラベル）のペアだけなので、回答例を書くより桁違いに安く集まる。実際の問い合わせログから数百件を仕分ければ足りることが多い。

分類器の利点は、生成モデルから独立していることにある。閉じた API モデルを使っていても自前で置けるし、プロンプトへの注入も届かない。判定は確率で返るので、[分類器の確信度の記事](/blog/ja/classification-confidence/)で書いたとおり、閾値と較正を検証セットで調整できる。「ボタンが押せない」のような境界の質問を弾いてしまう率と、無関係な質問を通してしまう率を別々に測り、どちらを優先するかを業務で決める。EC サイトなら、買う気のある客を弾くほうが損失が大きいことが多い。

境界の設計もここで決まる。「このセーターの洗い方」は FAQ にはないが商品には関係する。こういう質問を範囲外として断るのか、担当者につなぐ列に振り分けるのかは、分類器のラベル設計の問題であって、生成モデルの問題ではない。

### 生成モデルには「文脈だけから答える」を躾ける

門を 2 つ抜けた質問だけが生成モデルに届く。それでも、モデルが検索結果を無視して自分の知識で答えてしまうことはある。ここで前節の RAG ＋ LoRA が効く。「与えられた FAQ の抜粋だけから答え、抜粋に答えがなければ『該当する情報がありません』と返す」というふるまいを LoRA で学習させる。教師データは、FAQ の抜粋を付けた質問と、抜粋を意図的に外した質問の両方を作ればよい。後者の正解は定型の断り文で、前節で書いたとおり入力から判定できる条件なので LoRA で安定して学べる。

システムプロンプトだけでこれをやると、断る条件を長々と書くことになり、毎リクエストのトークンが増えるうえに守られにくい。LoRA に移せばプロンプトは短くて済む。

### 出力を検証してから返す

最後に、生成した回答が検索結果に根拠を持つかを確認する層を置くこともできる。回答と検索結果のペアを NLI モデルか別の LLM に渡し、「回答は文脈から導けるか」を判定させる。導けなければ回答を捨てて定型文に差し替える。生成モデルがすり抜けて一般知識で答えた場合の最後の網になる。推論が 1 回分増えるので、返品や決済のように誤答の代償が大きい話題に絞って入れる。

### 層を重ねる理由

どの層も単独では穴がある。プロンプトは長い会話と注入に弱く、検索スコアは類似と関連を取り違え、分類器は境界の質問で迷い、LoRA は学習データにない言い回しで崩れる。ただし穴の場所がそれぞれ違うので、重ねると通り抜ける質問は急に減る。EC サイトの FAQ ボットなら、入力分類器と検索スコアの閾値で範囲外を止め、LoRA で「文脈にないことは言わない」を躾け、出力検証は誤答が高くつく話題に絞る、という構成が現実的な落としどころになる。

## 選び方の手順

1. まずプロンプトだけで作り、測る。システムプロンプトと few-shot 例で到達できる線を確認する。ここで十分ならそれで終わりだ。
2. 誤答を「知識の失敗」と「ふるまいの失敗」に仕分ける。混ざっているのが普通で、比率を見る。
3. 知識の失敗には RAG。索引を作り、検索品質を単独で測る。取れているのに答えが違うなら生成側、取れていないなら検索側を直す。
4. ふるまいの失敗には LoRA。数百〜数千件の理想的な応答例を用意して学習する。閉じた API モデルなら提供者のファインチューニング API を使う。RAG と併用するなら、学習データも「文脈付きの質問 → 文脈に基づく回答」の形にする。
5. それでも足りなければフルファインチューニング。ドメインのずれが深く、数万件以上のデータと GPU があり、一般能力の退行を測る体制があるときに限る。

| 状況 | 向いている選択 |
| --- | --- |
| 社内文書・仕様・規約に基づいて答えさせたい | RAG |
| 情報が日々更新される | RAG |
| 出典を示す必要がある、利用者ごとに見せてよい情報が違う | RAG |
| 口調・出力形式・用語・断り方を揃えたい | LoRA（または提供者のファインチューニング API） |
| 「文脈にないことは言わない」を徹底したい | RAG ＋ LoRA（RAFT 型のデータで） |
| 特定ドメイン（EC サイトの FAQ など）以外の質問には答えさせたくない | 入力分類器 ＋ 検索スコアの閾値で止め、LoRA で断り方を躾ける |
| 専門用語での検索精度が低い | 埋め込みモデル / 再ランカーのファインチューニング |
| 事前学習にほとんどない言語・記法に対応したい | 継続事前学習 ＋ SFT（フル、または大きい $$r$$ の LoRA） |
| 大量トラフィックで推論トークンを削りたい | ふるまい部分を LoRA に移し、プロンプトを短くする |

手順は 5 つあるが、実際には 1 と 2 でほとんど決まる。誤答を仕分けた時点で、読ませるべきか躾けるべきかは見えている。作り替える判断が要るのは、その両方を試したあとでよい。
