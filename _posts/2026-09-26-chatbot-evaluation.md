チャットボットの「精度」は 1 つの数字では表しにくい。検索が正しい文書を取れたか、回答がその文書に基づいているか、質問に答えきれているか、断るべき質問を断れたかは、別々の部品で起きる別々の失敗だからだ。平均して 1 つの値にすると、どこを直せばよいかが分からなくなる。

この記事では、部品ごと・失敗の種類ごとに、指標、評価データ、判定者を分けて測る方法を整理する。オフラインの評価セットで変更による劣化を検出し、オンラインでは実際の利用者の行動を見る。

## 「正しい」の定義を先に分ける

誤答にも種類があるので、先に分けておく。

正確さ（correctness）は答えが事実と合っているかで、正解と照合して測る。忠実さ（faithfulness）は答えが与えた文脈から導けるかで、正解がなくても文脈があれば判定できる。RAG ではこの 2 つがずれることがある。文脈には忠実でも、文脈自体が古くて事実と合わない場合は、索引の問題である。事実としては正しくても、文脈にない知識をモデルが補っている場合は、生成側の問題である。

有用性（helpfulness）は、質問に過不足なく答えているかである。返品期限を聞かれて「返品できます」とだけ返すのは、正しくても役に立たない。方針遵守は、範囲外や有害な質問を断り、範囲内の質問は断っていないかを見る。形式は、指定した JSON、長さ、口調を守っているかを見る。

[以前の記事](/blog/ja/rag-lora-finetuning/)で、チャットボットの失敗を「知らない」と「ふるまいがずれる」に分けた。正確さと忠実さは「知らない」側、有用性・方針遵守・形式は「ふるまいがずれる」側にあたる。評価も同じ分け方にしておくと、結果からそのまま対処を選べる。

## 部品ごとに測る

  <figcaption>上流の失敗は下流で取り返せないので、範囲判定、検索、生成の順に部品単位で評価し、最後に全体を通して測る。</figcaption>
</figure>

パイプラインは範囲判定、検索、生成の順に進む。検索が正しい文書を取れなければ、生成モデルがいくら高性能でも正しい答えは出ない。そのため評価も上流から順に、部品単位で行う。

### 検索は、正解パッセージが上位に入るかを見る

評価データは（質問, 正解を含むパッセージ）のペアで、正解は人が付ける。中心になる指標は Recall@k である。上位 $$k$$ 件をプロンプトに入れるなら、その中に正解がなければ生成側ではほぼ答えられない。順位も見たい場合は MRR や nDCG を使う。定義は[検索評価指標の記事](/blog/ja/information-retrieval-metrics/)にまとめた。

この評価は LLM を呼ばず、結果も毎回同じになる。数秒で終わるので、チャンク分割、埋め込みモデル、再ランカーを変えるたびに実行する。

### 範囲判定は、弾きすぎと通しすぎを別々に数える

範囲判定は分類問題なので、混同行列で評価する。範囲内の質問を断る率（過剰拒否）と、範囲外の質問を通す率は別々に集計する。EC サイトなら過剰拒否は売上の損失、通しすぎはブランドや法務のリスクで、重さが違うからだ。

見落としやすいのは過剰拒否である。典型的な範囲内の質問と明らかな範囲外の質問だけで評価すると、範囲外に見える正当な質問を断っていても数字に表れない。Röttger et al.（2024）の XSTest は、危険に見えるが無害な質問を集めて断りすぎを測るテストセットである。同じように、自社ドメインの「境界に見えるが正当な質問」を評価セットに入れておく。判定が確率で出るなら、[分類器の確信度の記事](/blog/ja/classification-confidence/)の手順で閾値と較正を調整する。

### 生成は、正解と照合するか文脈と照合するかを分ける

生成は出力が自由文なので、評価に最も手間がかかる。

「返品期限は 14 日」のように正解を用意できる質問は、正解との一致で測る。短い答えなら完全一致や単語単位の F1 が使える。言い回しが違っても意味が同じなら正解にしたいので、実務では LLM に「正解と同じ内容か」を判定させることが多い。BLEU や ROUGE は自由文の回答では人の判断との相関が低いので、主な指標にはしない。

正解を用意しにくい質問は、文脈と照合する。回答を個々の主張に分解し、それぞれが検索結果から導けるかを判定して、導けた主張の割合を忠実さのスコアにする。

$$
\mathrm{faithfulness} = \frac{\text{文脈から導ける主張の数}}{\text{回答に含まれる主張の数}}
$$

  <img src="{{ '/assets/img/claim-faithfulness.svg' | relative_url }}" alt="主張単位の忠実さ評価。回答を 4 つの主張に分解し、それぞれを検索結果と照合する。3 つは文脈に根拠があり、1 つは根拠がないので、忠実さは 3/4 = 0.75 になる">
  <figcaption>回答を主張に分解し、1 つずつ文脈と照合する。回答全体に点数を付けるより安定し、根拠のない主張も特定できる。</figcaption>
</figure>

RAGAS（Es et al., 2023）や FActScore（Min et al., 2023）がこの方式を採っている。回答全体に 1〜5 点を付けるより判定がぶれにくく、根拠のない箇所が主張単位で分かる。

有用性は、質問と回答のペアを見て、質問に答えているか、不足している情報はないかを判定する。RAGAS は回答から質問を逆に生成し、元の質問との類似度を answer relevance としている。実務では「この回答で利用者の用件は片付くか」という基準を rubric に書いて LLM に採点させるほうが、目的に合うことが多い。

形式は機械的に確認する。JSON はスキーマ検証、長さは文字数、禁止表現は正規表現で調べれば、LLM に判定させるより確実である。

### 最後は通しで測る

部品ごとの評価が良くても、つなげると悪くなることがある。たとえば、検索結果 5 件に正解が含まれているのに、残り 4 件に影響されて誤答する失敗は、部品単位では検出できない。質問から最終回答までを通して評価し、部品ごとの結果と差があれば、部品間の受け渡しを疑う。

複数ターンの会話では、ターン単位と会話全体を分けて評価する。ターン単位では、直前までの履歴を与えて応答を判定する。会話全体では、用件が片付いたかを人またはモデルが判定し、タスク成功率として集計する。

## 判定者を選ぶ

完全一致、スキーマ検証、正規表現、検索の Recall のように機械的に判定できる項目は、機械的に判定する。再現性があり、コストがほとんどかからず、判定者の癖に左右されない。

自由文の判定には LLM を使う。Zheng et al.（2023）は、GPT-4 による回答の優劣判定が人間の判定と 8 割強一致し、人間どうしの一致率と同程度だったと報告している。ただし LLM の判定には偏りがあるので、対策を入れる。

2 つの回答を比較させると、先に提示したほうを選びやすい（Wang et al., 2023）。順序を入れ替えて 2 回判定し、一致した場合だけ採用する。長い回答を高く評価する傾向もあるので、rubric に「不要な情報は減点する」と書き、長さは別に測る。生成モデルと同じモデルは自分の出力を高く評価する（Panickssery et al., 2024）ため、判定には別のモデルを使う。1〜10 点の絶対評価は基準がぶれやすいので、合否の 2 値か A と B の比較にする。G-Eval（Liu et al., 2023）のように評価手順を明文化させる方法も、ある程度効く。

LLM 判定者も 1 つの分類器なので、使う前に精度を確認する。人手ラベル 100〜200 件との一致率（Cohen の κ など）を出し、低ければ rubric を直す。ARES（Saad-Falcon et al., 2024）はこの考え方を枠組みにしたもので、少量の人手ラベルで LLM 判定の偏りを補正し、信頼区間を出す。

人手評価は最も信頼できるが、コストも最も高い。全件を人が見る運用は続かないので、人手は LLM 判定者の検証用ラベル作りと定期的な監査に充てる。

## 評価セットの作り方

質問はできるだけ本番のログから取り、匿名化して実際の言い回しのまま使う。ログがない立ち上げ期は、FAQ や文書から LLM に質問を生成させる。ただし生成された質問は文書と言葉づかいが似るため、検索の Recall が実際より高く出る。ログが溜まったら置き換える。

質問は種類ごとに層に分ける。意図（配送・返品・支払いなど）、範囲外の質問、曖昧な質問、境界に見えるが正当な質問、プロンプト注入を試みる入力、複数ターンの会話などである。全体の平均だけでは、返品や決済のように件数の少ない種類の失敗が目立たない。業務上の損失が大きい種類は、件数が少なくても個別に集計する。

必要な件数は推定の誤差から見積もる。正答率 $$p$$ を $$n$$ 件で推定したときの標準誤差は $$\sqrt{p(1-p)/n}$$ で、$$p = 0.8$$ なら 95% 信頼区間の幅は次のようになる。

| 件数 | 95% 信頼区間 |
| --- | --- |
| 50 | ±11 pt |
| 100 | ±8 pt |
| 400 | ±4 pt |
| 1000 | ±2.5 pt |

100 件では 5 pt の改善は誤差と区別できない。層ごとの誤差はその層の件数で決まるので、意図ごとに 100 件以上を目安にする。2 つの構成を比べる場合は、同じ質問集合で質問ごとの差を取れば、必要な件数はずっと少なくて済む。

評価セットは固定し、バージョンを付ける。評価セットの質問を few-shot 例やプロンプト調整に使うと、その質問でだけ点数が上がり、評価にならなくなる。開発中に繰り返し見る開発セットと、最後にだけ使うテストセットを分けておく。

## オフラインとオンラインの役割分担

オフライン評価の目的は、変更による劣化（回帰）を本番に出る前に見つけることである。プロンプト、モデル、索引、チャンク分割を変えるたびに評価セットを実行し、ベースラインと比べる。CI に組み込み、閾値を下回った変更はマージしない。機械的な指標は毎回、LLM による判定は主要な層だけにすれば、コストを抑えられる。

オンライン指標からは、評価セットにない質問での挙動が分かる。使えるのは、利用者の評価ボタン、人への引き継ぎ率、同じ質問の言い直し率、用件が片付いて終わった会話の割合などである。いずれも間接的な指標で、評価ボタンは押す利用者が偏る。構成の比較で最も信頼できるのは A/B テストで、利用者を 2 つの構成に振り分けて引き継ぎ率や解決率を比べる。

本番トラフィックからは定期的にサンプルを取り、オフラインと同じ判定にかける。質問の分布の変化や新しい種類の質問を確認し、評価セットに追加する。

## Langfuse で一つの画面にまとめる

ここまでの運用を 1 つのツールで行うなら、筆者は Langfuse を選ぶ。MIT ライセンスの OSS で、Docker Compose でセルフホストでき、クラウド版もある。トレース、スコア、データセット、人手のラベル付けを同じ画面で扱える。

### トレースに部品ごとの記録を残す

トレースは Python か JS の SDK、または OpenTelemetry で送る。1 回の問い合わせが 1 つのトレースになり、範囲判定の結果、検索で取れたチャンク、生成のプロンプトと出力が入れ子で記録される。LangChain、LlamaIndex、OpenAI SDK などとの統合があり、既存のコードに数行足せば済むことが多い。複数ターンの会話はセッションにまとまり、会話単位の評価に使える。部品ごとの評価には、この記録を使う。

### スコアの出どころを 1 か所に集める

Langfuse では、評価結果をすべて「スコア」としてトレースに付ける。Recall@k やスキーマ検証の結果は SDK から送る。LLM 判定者は、評価テンプレートを登録しておくと本番トレースのサンプルに自動で実行される。人手のラベルは次に述べるアノテーションキューから付ける。利用者の評価ボタンも SDK からスコアとして送れる。

出どころの違うスコアが同じトレースに並ぶので、LLM 判定と人手ラベルの一致率は、画面でフィルタしてエクスポートすれば計算できる。

### 人手のラベルはアノテーションキューで回す

最初にスコアの定義を作る。名前、型（数値、カテゴリ、真偽）、取りうる値の範囲を決めておくと、レビュアーごとの付け方のばらつきが減る。次に、ラベルを付けたいトレースをフィルタかサンプリングでキューに入れる。レビュアーは質問、検索結果、回答を見ながら順にラベルを付け、ラベルはスコアとして保存される。

主な用途は、LLM 判定者の検証に使う 100〜200 件のラベル作り、定期的な監査、境界に見える質問の仕分けである。LLM 判定者のスコアが低かったトレースだけをキューに入れると、人が見る件数を抑えつつ、判定者が誤りやすいケースも分かる。

### トレースをそのまま評価セットにする

トレースの画面で「データセットに追加」を選ぶと、その質問と文脈が評価項目になる。期待する出力はあとから編集できる。ログから評価セットを更新する作業は、この操作で行う。

データセットに対しては SDK から実験（run）を実行し、run どうしを画面で比較する。プロンプトもバージョン管理されるので、どの run がどのプロンプトによるものかを追える。

### 運用の流れ

本番トレースのサンプルに LLM 判定者を実行し、スコアの低いものをアノテーションキューに入れて人がラベルを付け、必要なものをデータセットに追加する。構成を変えたら、そのデータセットで run を実行して前回と比べる。この流れは Langfuse に依存しないので、別のツールでも同じように組める。

## 落とし穴

評価の設計で起きやすい問題を挙げる。

- 平均点だけを見る。どの部品を直すべきかが分からないので、数字が動いたら部品ごとの数字を先に見る。
- 生成と判定に同じモデルを使う。自分の出力を高く評価するので、スコアが高く出る。
- 索引の文書から生成した質問で検索を評価する。Recall が高く出る。
- 境界に見えるが正当な質問を評価セットに入れない。過剰拒否を検出できない。
- 評価セットの質問を few-shot 例やプロンプト調整に使う。点数は上がるが、本番の品質は変わらない。
- 意図ごとの損失の違いを無視して平均する。返品や決済のように損失の大きい失敗が目立たなくなる。

## 手順

1. 失敗例を集める。ログ（なければ想定される質問）から誤答を集め、正確さ・忠実さ・有用性・方針遵守・形式に分類する。
2. 部品ごとに評価データを作る。検索には（質問, 正解パッセージ）、範囲判定には（質問, ラベル）、生成には（質問, 文脈, 正解または rubric）を用意する。
3. 機械的に判定できる指標（Recall@k、混同行列、スキーマ検証）から入れる。
4. LLM 判定者を作り、人手ラベルで精度を確認してから使う。
5. CI に組み込み、変更のたびにベースラインと比べる。
6. 本番ではオンライン指標を見て、サンプルを評価セットに追加する。

測る対象ごとの指標、評価データ、判定者は次のとおり。

| 何を測るか | 指標 | 評価データ | 判定者 |
| --- | --- | --- | --- |
| 検索 | Recall@k、MRR、nDCG | 質問と正解パッセージ | 機械 |
| 範囲判定 | 過剰拒否率、通過率、混同行列 | 質問とラベル | 機械 |
| 正確さ | 正解との一致率 | 質問と正解 | 機械、または LLM |
| 忠実さ | 支持された主張の割合 | 質問と文脈 | LLM（人手で検証） |
| 有用性 | rubric 採点、ペア比較 | 質問と rubric | LLM（人手で検証） |
| 形式 | スキーマ、長さ、禁止表現 | 仕様 | 機械 |
| 通し | タスク成功率 | 会話 | 人、または LLM |
| 本番 | 引き継ぎ率、言い直し率、A/B | ログ | 利用者の行動 |

「精度」を説明するには、この表の各行の数字を出すことになる。1 つの数字が必要なら、各行を業務上の損失で重み付けして合算する。ただし、その数字からは直す箇所が分からないので、報告用の合算値と開発用の表は分けて持つ。
