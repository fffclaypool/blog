チャットボットの「精度」は 1 つの数字にならない。検索が正しい文書を取れたか、回答がその文書に基づいているか、質問に答えきれているか、答えるべきでない質問を断れたか。これらは別の部品の別の失敗で、1 つに平均すると、どこを直せばよいかが見えなくなる。

評価は「どの部品が、どの種類の失敗を、どれだけ起こすか」を別々に測る作業になる。部品ごとに指標と評価データと判定者を分け、オフラインの評価セットで変更のたびに回帰を止め、オンラインでは実際の利用者の行動を見る。以下はその組み立て方だ。

## 「正しい」の定義を先に分ける

同じ「間違い」でも中身は違う。

正確さ（correctness）は、答えが事実と合っているかで、正解を用意して照合する。忠実さ（faithfulness）は、答えが与えた文脈から導けるかで、正解がなくても文脈があれば判定できる。RAG ではこの 2 つがずれることがある。文脈には忠実だが、文脈自体が古くて事実と合わない答え。事実としては正しいが、文脈にない知識でモデルが勝手に補った答え。前者は索引の問題、後者は生成側の問題で、直す場所が違う。

有用性（helpfulness）は、質問に答えきれているか、余計なことを言っていないかだ。正確でも「返品できます」だけでは、期限を聞いた客の役に立たない。方針遵守は、範囲外や有害な質問を断り、範囲内の質問を断りすぎていないか。形式は、指定した JSON や長さ、口調を守っているかを指す。

[以前の記事](/blog/ja/rag-lora-finetuning/)で、チャットボットの失敗を「知らない」と「ふるまいがずれる」に分けた。正確さと忠実さは前者、有用性・方針・形式は後者にあたる。評価も同じ線で分けておくと、結果から対処が読める。

## 部品ごとに測る

  <figcaption>上流の失敗は下流で取り返せないので、評価も範囲判定、検索、生成の順に部品単位で行い、最後に通しで測る。</figcaption>
</figure>

パイプラインは範囲判定、検索、生成の順に並ぶ。上流の失敗は下流で取り返せない。検索が正しい文書を取れなければ、生成がどれだけ賢くても正しい答えは出ない。だから評価も上流から順に、部品単位で行う。

### 検索は、正解パッセージが上位に入るかを見る

評価データは（質問, 正解を含むパッセージ）のペアで、正解は人が付ける。指標は Recall@k が主役だ。上位 $$k$$ 件をプロンプトに入れるなら、その中に正解が入っていなければ生成に望みはない。順位まで見たいなら MRR や nDCG を使う。定義は[検索評価指標の記事](/blog/ja/information-retrieval-metrics/)にまとめた。

この評価は決定的で、LLM を呼ばずに走る。数秒で終わるので、チャンク分割や埋め込みモデルや再ランカーを変えるたびに回す。

### 範囲判定は、弾きすぎと通しすぎを別々に数える

範囲判定は分類問題なので、混同行列で見る。範囲内の質問を断ってしまう率（過剰拒否）と、範囲外の質問を通してしまう率を別々に出し、1 つの精度に混ぜない。EC サイトなら過剰拒否は売上の損失、通しすぎはブランドや法務のリスクで、重みが違うからだ。

見落としやすいのは過剰拒否のほうだ。範囲内の質問だけで評価していると、断りすぎは表に出ない。Röttger et al.（2024）は、危険に見える言い回しの無害な質問を集めて断りすぎを測るテストセット（XSTest）を作った。同じ発想で、自社ドメインの「境界に見える正当な質問」を集めておく。判定が確率で出るなら、閾値と較正の調整は[分類器の確信度の記事](/blog/ja/classification-confidence/)の手順で行う。

### 生成は、正解と照合するか文脈と照合するかを分ける

生成の評価がいちばん厄介なのは、答えが自由文だからだ。

正解が用意できる質問（返品期限は 14 日、など）は、正解との一致で測る。短い答えなら完全一致か単語の F1。言い回しが違っても意味が同じなら正解にしたいので、実務では LLM に「正解と同じ内容か」を判定させることが多い。BLEU や ROUGE のような n-gram の重なりは、自由文の回答では人の判断とあまり相関しないので主指標にはしない。

正解が用意しにくい質問は、文脈との照合に切り替える。回答をひとつずつの主張に分解し、それぞれが検索結果から導けるかを判定して、支持された主張の割合を忠実さのスコアにする。

$$
\mathrm{faithfulness} = \frac{\text{文脈から導ける主張の数}}{\text{回答に含まれる主張の数}}
$$

  <img src="{{ '/assets/img/claim-faithfulness.svg' | relative_url }}" alt="主張単位の忠実さ評価。回答を 4 つの主張に分解し、それぞれを検索結果と照合する。3 つは文脈に根拠があり、1 つは根拠がないので、忠実さは 3/4 = 0.75 になる">
  <figcaption>回答を主張に分解して 1 つずつ文脈と照合する。回答全体に点を付けるより安定し、どの主張が根拠なしかまで分かる。</figcaption>
</figure>

RAGAS（Es et al., 2023）や FActScore（Min et al., 2023）はこの形で、主張単位に落とすことで「どこが根拠なしか」まで特定できる。回答全体に 1〜5 点を付けるより安定するし、直す箇所が分かる。

有用性は「質問に答えているか」「足りない情報はないか」を、質問と回答のペアで判定する。RAGAS は回答から逆に質問を生成させ、元の質問との類似度を answer relevance としているが、実務では「この回答で客の用事は済むか」という基準を書いた rubric で LLM に採点させるほうが目的に合う。

形式は機械で確認する。JSON ならスキーマ検証、長さなら文字数、禁止表現なら正規表現。LLM に頼む必要はなく、頼まないほうが確実だ。

### 最後は通しで測る

部品ごとの評価が全部良くても、つないだときに悪いことはある。検索結果が 5 件あって正解は入っているのに、他の 4 件に引きずられて答えを間違える、といった失敗は通しでしか見えない。質問から最終回答までを一括で評価し、部品評価との差分を見る。差があれば、部品のつなぎ目に問題がある。

複数ターンの会話は、ターンごとに直前までの履歴を与えて評価するのと、会話全体で用事が済んだかを評価するのを分ける。後者はタスク成功率として、会話ごとに人かモデルが判定する。

## 判定者を選ぶ

決定的な判定が使えるところでは、必ずそれを使う。完全一致、スキーマ検証、正規表現、検索の Recall。再現性があり、コストがゼロで、偏りがない。

自由文の判定には LLM を使う。Zheng et al.（2023）は GPT-4 に回答の優劣を判定させ、人間の判定との一致率が 8 割強で、人間同士の一致率と同程度だったと報告している。使えるが、癖がある。

2 つの回答を並べて比べさせると、先に出したほうを選びやすい（Wang et al., 2023）。順序を入れ替えて 2 回判定し、一致したときだけ採用する。長い回答を高く評価しがちでもあるので、rubric に「不要な情報は減点」と書き、長さは別途測る。判定者と生成モデルが同じだと自分の出力を高く評価する（Panickssery et al., 2024）ため、判定には別のモデルを使う。1〜10 点の絶対評価は基準がぶれるので、合否の 2 値か A と B の比較にするほうが安定する。G-Eval（Liu et al., 2023）のように評価手順を明文化させると多少ましになる。

忘れてはいけないのは、LLM 判定者も 1 つの分類器だということだ。信頼する前に精度を測る。人が付けたラベル 100〜200 件で判定者との一致率（Cohen の κ など）を出し、低ければ rubric を直す。ARES（Saad-Falcon et al., 2024）は、少量の人手ラベルで LLM 判定の偏りを補正して信頼区間を出す枠組みで、同じ発想を形式化したものだ。

人手評価は最も信頼できるが高い。役割は、LLM 判定者を検証するためのラベル作りと、定期的な監査に絞る。全件を人が見る運用は続かない。

## 評価セットの作り方

質問はどこから来るか。本番のログが第一で、匿名化して実際の言い回しのまま使う。ログがない立ち上げ期は、FAQ や文書から LLM に質問を生成させる。ただし生成された質問は文書の言葉をなぞるので、検索の Recall が実態より高く出る。ログが溜まりしだい置き換える。

質問は種類ごとに層別する。意図（配送・返品・支払いなど）、範囲外、曖昧な質問、境界に見える正当な質問、注入を試みる入力、複数ターン。全体の平均だけを見ると、件数の少ない返品や決済の失敗が薄まる。業務上の損失が大きい種類は、件数が少なくても別枠で集計する。

何件要るか。正答率 $$p$$ を $$n$$ 件で推定したときの標準誤差は $$\sqrt{p(1-p)/n}$$ で、$$p = 0.8$$ なら 95% 信頼区間の幅は次のようになる。

| 件数 | 95% 信頼区間 |
| --- | --- |
| 50 | ±11 pt |
| 100 | ±8 pt |
| 400 | ±4 pt |
| 1000 | ±2.5 pt |

100 件では 5 pt の改善が誤差に埋もれる。層ごとに見るならその層の件数で効くので、意図ごとに 100 件以上を目安にする。ただし 2 つの構成を比べるときは、同じ質問集合で対にして差を取れば、必要な件数はずっと少なくて済む。

評価セットは固定してバージョンを付ける。few-shot 例やプロンプト調整に評価セットの質問を使うと、そこだけ点が上がって意味がなくなる。開発中に何度も見る開発セットと、最後にだけ見るテストセットを分けておく。

## オフラインとオンラインの役割分担

オフライン評価は回帰を止めるためにある。プロンプト、モデル、索引、チャンク分割のどれかを変えるたびに評価セットを流し、ベースラインと比べる。CI に入れて、閾値を下回ったらマージしない。決定的な指標は毎回、LLM 判定は主要な層だけ、と使い分ければコストは抑えられる。

オンライン指標は、評価セットに入っていない質問で何が起きているかを教える。使えるのは、利用者の評価ボタン、人への引き継ぎ率、同じ質問の言い直し率、会話が用事を済ませて終わった率。どれも間接的で、評価ボタンは押す人が偏る。指標として一番信用できるのは A/B テストで、構成 A と B に利用者を分けて引き継ぎ率や解決率を比べる。

本番トラフィックからは定期的にサンプルを抜き、オフラインと同じ判定を流す。分布が変わっていないか、新しい種類の質問が増えていないかを見て、評価セットに足す。評価セットは作って終わりではなく、ログから育てるものだ。

## Langfuse で一つの画面にまとめる

ここまでの運用を一つの道具で回すなら、筆者は Langfuse を使う。OSS（MIT ライセンス）で Docker Compose でセルフホストでき、クラウド版もある。トレース、スコア、データセット、人手のラベル付けが同じ画面にあり、前節のオフラインとオンラインの往復がそのまま組める。

### トレースに部品ごとの記録を残す

Python か JS の SDK、または OpenTelemetry でトレースを送る。1 回の問い合わせが 1 つのトレースになり、その中に範囲判定の結果、検索で取れたチャンク、生成に渡したプロンプトと出力が入れ子で残る。LangChain、LlamaIndex、OpenAI SDK などの統合があるので、既存のコードに数行足せば済むことが多い。複数ターンの会話はセッションでまとまり、会話単位の評価にも使える。

部品ごとに測るには、部品ごとの記録が要る。トレースがその土台になる。

### スコアの出どころを 1 か所に集める

Langfuse では評価結果をすべて「スコア」としてトレースに付ける。Recall@k やスキーマ検証のような機械判定は SDK から送る。LLM 判定者は Langfuse 側に評価テンプレートを登録しておくと、本番トレースのサンプルに対して自動で走る。人手のラベルは次のアノテーションキューから付く。利用者の評価ボタンも SDK からスコアとして送れる。

出どころの違うスコアが同じトレースに並ぶので、LLM 判定と人手ラベルの一致率を出す作業が、画面のフィルタとエクスポートで済む。前々節で書いた「判定者を信頼する前に精度を測る」が、特別な仕組みなしにできる。

### 人手のラベルはアノテーションキューで回す

まずスコアの定義を作る。名前、型（数値、カテゴリ、真偽）、取りうる範囲を決めておくと、レビュアーごとに付け方がぶれない。次に、ラベルを付けたいトレースをフィルタかサンプリングでキューに入れる。レビュアーはキューを開き、質問、検索結果、回答を見ながら順にラベルを付けていく。付けたラベルはそのままスコアとして保存される。

使い道は、LLM 判定者を検証するための 100〜200 件のラベル作り、定期的な監査、境界に見える質問の仕分け。LLM 判定者のスコアが低かったトレースだけをキューに流せば、人が見る件数を絞りながら、判定者が間違えやすい場所も分かる。

### トレースをそのまま評価セットにする

トレースの画面から「データセットに追加」を押すと、その質問と文脈が評価項目になる。期待する出力は後から編集できる。評価セットを「ログから育てる」という前節の話は、この操作の繰り返しだ。

データセットに対しては SDK から実験（run）を回し、run どうしを画面で並べて比べる。プロンプトはバージョン管理されるので、どのプロンプトでどの run を取ったかが追える。変更のたびに run を回してベースラインと比べる、という回帰の運用もここに乗る。

### 運用の形

本番のトレースに LLM 判定者をサンプルで走らせ、低スコアのものをアノテーションキューに流し、人がラベルを付け、必要なものをデータセットに足す。変更があればそのデータセットで run を回し、前の run と比べる。この一巡が Langfuse の画面の中で閉じる。道具が変わっても、この形自体は同じだ。

## 落とし穴

平均点だけで議論すると、どの部品を直せばよいか分からない。数字が動いたら、まず部品ごとの数字に戻る。

生成モデルと判定モデルが同じだと、自己選好で高く出る。評価セットが索引から生成されていると、検索の Recall が過大になる。範囲内の質問しか評価していないと、過剰拒否が見えない。評価セットの質問がプロンプトに漏れていると、点が上がっても本番は変わらない。意図ごとの損失の違いを無視して平均すると、返品や決済のような高くつく失敗が薄まる。どれも、評価の設計を最初に決めておけば避けられる。

## 手順

1. 失敗を集める。ログか想定から誤答を集め、正確さ・忠実さ・有用性・方針・形式に仕分ける。
2. 部品ごとに評価データを作る。検索は（質問, 正解パッセージ）、範囲判定は（質問, ラベル）、生成は（質問, 文脈, 正解または rubric）。
3. 決定的な指標から入れる。Recall@k、混同行列、スキーマ検証。
4. LLM 判定者を作り、人手ラベルで検証してから使う。
5. CI に組み込み、変更ごとにベースラインと比べる。
6. 本番ではオンライン指標を見て、サンプルを評価セットに戻す。

| 何を測るか | 指標 | 評価データ | 判定者 |
| --- | --- | --- | --- |
| 検索 | Recall@k、MRR、nDCG | 質問と正解パッセージ | 機械 |
| 範囲判定 | 過剰拒否率、通過率、混同行列 | 質問とラベル | 機械 |
| 正確さ | 正解との一致率 | 質問と正解 | 機械、または LLM |
| 忠実さ | 支持された主張の割合 | 質問と文脈 | LLM（人手で検証） |
| 有用性 | rubric 採点、ペア比較 | 質問と rubric | LLM（人手で検証） |
| 形式 | スキーマ、長さ、禁止表現 | 仕様 | 機械 |
| 通し | タスク成功率 | 会話 | 人、または LLM |
| 本番 | 引き継ぎ率、言い直し率、A/B | ログ | 利用者の行動 |

「精度」を一言で言おうとすると、結局この表の各行を埋めることになる。1 つの数字がどうしても要るなら、業務上の損失で重み付けして足せばよい。ただしその数字では直す場所は決められないので、報告用の 1 行と、開発用の表を分けて持つ。
