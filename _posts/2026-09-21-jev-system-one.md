LLM に「この問い合わせは返金依頼か？」と聞くとき、構造化出力を使えば、`yes` / `no` のどちらに該当するかと、その「確信度」を申告させることはできる。しかし、この確信度は自己申告なので過信気味になり、当てにしにくい。代わりにトークンの logprob を読んでも、生成モデルの確率は語彙全体との競合や表記ゆれで歪んでいる。TypeSafe が公開している Jev は、不確かさを確率分布として返すことを最初から目的に作られたモデルで、テキストは生成しない。状態（state）と型付きの質問（questions）を受け取り、選択肢に対する確率分布と確信度を返す。

この記事では、公式ドキュメント（[docs.typesafe.ai](https://docs.typesafe.ai/introduction)）をもとに Jev の入出力と学習方針を整理し、同じく「生成しない」モデルの BERT 系 Transformer Encoder ＋ 分類ヘッドとの違いを見ていく。Jev の内部アーキテクチャ（層数、Encoder か Decoder か、など）は公開されていないので、以下の比較は、公開されているインターフェースと学習目標に基づいている。

## Jev とは

TypeSafe は Jev を「最初の System One モデル」と呼んでいる。名前は Kahneman の『ファスト＆スロー』に由来し、速く直感的な判断（System 1）を担うモデルを意味する。ドキュメントは対象範囲を「十分な文脈があれば、知識のある人が数秒で下せる種類の判断」と説明している。

API のエンドポイントは1本（`POST /v1/systemone`）で、リクエストは次の3要素からなる。

- **`state`**: 評価対象の内容。文字列・JSON オブジェクト・配列のいずれか。テキストのみ（画像・音声は未対応）
- **`questions`**: state に対する質問の集合。各質問は `type`・`instructions`・`criteria` を持つ
- **`model`**: `jev-latest` など

質問のタイプは3種類に限られ、TypeSafe はこれを AI プリミティブと呼んでいる。

| 質問タイプ | 問い | 返り値 |
| --- | --- | --- |
| **Choice** | 選択肢のどれか？ | `choice`, `probabilities`, `confidence` |
| **Score** | 順序付きの段階のどこか？ | `score`, `legend`, `probabilities`, `confidence` |
| **Noul** | この命題は真か？ | `noul`（0〜1の確率） |

1つのリクエストに複数の質問を入れられ、すべての質問は同じ state に対して並列かつ独立に評価される。質問を増やしてもレスポンス時間はほとんど変わらず、ある質問の答えが別の質問の文脈になることもない。

## 返り値は確率分布とその要約

バグ報告の深刻度を3段階で問う Score のレスポンス例を、ドキュメントから引用する。

```json
{
  "model": "jev-1.13.0",
  "answers": {
    "bug_severity": {
      "type": "score",
      "score": 1.43,
      "confidence": 0.35,
      "legend": {
        "0": "Cosmetic; no impact to functionality",
        "1": "Broken or degraded feature, but workaround exists",
        "2": "Blocking issue; no workaround exists"
      },
      "probabilities": { "0": 0.0, "1": 0.57, "2": 0.43 }
    }
  }
}
```

返り値の意味を数式で確認する。$$C$$ 個の選択肢（または段階）に対する確率分布を $$p = (p_0, \ldots, p_{C-1})$$、$$\sum_i p_i = 1$$ とする。

- **Choice** の `choice` は $$\arg\max_i p_i$$ で、確率が最大の選択肢を指す。
- **Score** の `score` は段階番号の期待値 $$\sum_{i=0}^{C-1} i \cdot p_i$$ にあたる。上の例では $$0 \times 0.0 + 1 \times 0.57 + 2 \times 0.43 = 1.43$$ で、レベル1と2の間のやや1寄りの位置を表す。
- **`confidence`** は、分布 $$p$$ の尖り具合を $$[0, 1]$$ の1つの値にまとめた統計量で、全確率が1つの選択肢に集まれば1.0になり、一様に近づくほど0に近づく。ドキュメントのデモは $$\frac{C \cdot \max_i p_i - 1}{C - 1}$$ で近似していて、厳密な定義は公開されていない。
- **Noul** は「真である確率」を1つ返す。0.5は「yes と no が同確率」という意味で、「中程度」という意味ではない。

`confidence` は `probabilities` から導出される二次的な値にあたる。閾値で分岐したいだけなら `confidence` を使えば足りる。分布全体が返ってくるので、用途に合わせて別の統計量（エントロピーなど）を自分で計算してもよい、とドキュメントに明記されている。

## 学習方針は RLHF ではなく RLCD

TypeSafe が最も強調しているのは学習目標の違いで、事前学習済み言語モデルの後段学習として次の3つを並べている。

| 手法 | 目標 | 生み出したもの |
| --- | --- | --- |
| RLHF（Reinforcement Learning from Human Feedback） | 人間が好む応答 | チャットボット |
| RLVR（Reinforcement Learning with Verifiable Rewards） | 検証可能な報酬（数学など） | 推論モデル |
| RLCD（Reinforcement Learning for Calibrated Decisions） | 較正された確率での判断 | System One モデル（Jev） |

RLHF は、モデルの複数の応答に人間が優劣を付け、その好みを報酬モデルとして学習させ、強化学習で「人間に好まれる応答」に寄せていく手法で、InstructGPT や ChatGPT はこの手法から生まれた。ドキュメントによれば、TypeSafe の共同創業者 Diogo Almeida はその共同発明者の1人にあたる。目的が「人間が好む」ことなので、自信ありげな断定や迎合（sycophancy）も報酬を得やすく、出力分布が特定のスタイルに偏る mode dropping も起きる。

RLVR は、数学の答え合わせやテストの通過のように、機械的に正誤を検証できる報酬で学習する手法で、o1 系や DeepSeek-R1 に代表される推論モデルを生んだ。正確さは上がるが、長い思考過程を生成するぶん、遅く高価になる。

RLCD は、どちらとも目的が異なる。人間の好みでも生成した答えの正誤でもなく、較正された確率を返すこと自体を学習目標にしている（報酬の具体的な設計は公開されていない）。出力について約束しているのは、テキストを生成しないこと、判断と確率を返すこと、確率が高いほど正解である見込みが実際に高いことの3点になる。

3点目が較正（calibration）で、確率0.8を付けた予測群のうち、実際に約80%が正解している状態を指す。[以前の記事](/blog/ja/classification-confidence/)で見たように、通常のニューラル分類器は系統的に過信し、RLHF を施した LLM はさらに較正が崩れる。TypeSafe は、較正を後付けの補正ではなく学習目標に据えたと主張している。

ただし、ドキュメント自身も注意しているとおり、較正は予測群に対する統計的な性質で、個々の答えの正しさは保証しない。「confidence 1.0」は「分布が1点に集中している」という意味で、「必ず正しい」という意味ではない。

## Transformer Encoder 分類器との比較

BERT・RoBERTa・DeBERTa などの Encoder に分類ヘッドを載せたモデルも、「生成しない」「閉じたラベル集合に対する確率分布を返す」という点で Jev とよく似ている。以下で共通点と違いを順に見る。

  <figcaption>左：Encoder 分類器はラベル数 C を学習時に固定し、1系列につき1つの分布を返す。右：Jev はラベル集合を自然言語の criteria としてリクエストごとに受け取り、1つの state に対する複数の質問を独立に評価する。</figcaption>
</figure>

### 共通点

- どちらも自由文を生成せず、事前に決めた候補集合上の確率分布を出力する
- そのため、Decoder LLM で問題になる「語彙全体との競合」「表記ゆれによる確率の分裂」「複数トークンの長さバイアス」は、少なくともインターフェース上は起きない
- 確率の argmax がそのまま判断になり、閾値運用や順位付けにも使える

### 違い1：ラベル空間をどこで定義するか

Encoder 分類器では、ラベル集合は学習時にヘッドの出力次元 $$C$$ として固定される。ラベルを1つ増やすには、ヘッドを作り直して再学習する必要がある。ラベルの意味はデータから暗黙的に学ばれるだけで、モデルは「クラス2が何を意味するか」を言葉としては知らない。

Jev では、ラベル集合をリクエストごとに自然言語の `criteria` として渡す。Choice なら `{"returns": "Exchanges, wrong or damaged items", ...}` のような対応表、Score なら段階ごとの説明文の配列を渡す。同じ重みがすべての利用者とすべてのタスクに使われ、ファインチューニングも LoRA も提供されない。ドメイン知識は `state` と `criteria` の書き方で与える。

式で書くと、Encoder 分類器は $$p = \mathrm{softmax}(W \cdot \mathrm{Enc}(x)_{\mathrm{[CLS]}})$$ で、$$W \in \mathbb{R}^{C \times k}$$ が固定されている。これに対して Jev は $$p = f(x,\ \text{instructions},\ \text{criteria})$$ という、ラベルの記述そのものを入力に含む関数になっている。これはゼロショット分類の形で、Encoder 系では NLI ベースのゼロショット分類（各ラベルを仮説文にして entailment 確率を取る）に近い。ただし Jev は、単発の NLI としてではなく、「候補集合上の較正された分布を返す」タスクとして最初から学習している。

### 違い2：1系列1タスクか、1 state N 質問か

Encoder 分類器は `[CLS] x [SEP]` を1回通して1つの分布を返す。3つの判断が欲しければ、3つのヘッドを用意する（マルチタスク学習）か、3回実行する。

Jev は1つの state に対して任意個の質問を並列かつ独立に評価する。ドキュメントはこれを「投機的ファンアウト」と呼び、必要になりそうな質問はすべて投げて、コード側で要るものだけ使うことを勧めている。追加コストは質問ぶんのトークンだけで、レイテンシはほぼ変わらないとされている。

独立に評価する点は Encoder のマルチタスクヘッドと同じに見えるが、Jev では、質問の追加や削除が他の質問の答えに影響しないと明記されている。Decoder LLM に複数の判断を1つのプロンプトで頼むと、前の答えが後の答えに影響する問題（context rot）が起きるが、Jev では設計上これが起きない。

### 違い3：確率の出どころと較正

Encoder 分類器の確率は、ロジットの softmax から得られる。[以前の記事](/blog/ja/classification-confidence/)で整理したとおり、少量データでファインチューニングすると0.99付近に張り付く過信が起きやすく、温度スケーリングなどの事後較正が実質的に必須になる。ただし、ラベル空間が固定で検証セットも作りやすいので、較正自体は難しくない。

Jev は較正を学習目標に含めていて（RLCD）、出荷時点で較正されていることを特徴として挙げている。また、Score 型は段階の期待値として「1.43」のような中間値を返せる。Encoder の名義ラベル分類にはこれに相当する出力がなく、順序回帰として別に設計する必要がある。

一方で、Jev の較正を自分のデータで検証する方法は、Encoder の場合と変わらない。検証セットに対して信頼度ダイアグラムを描き、ECE を測る。ドキュメントも「閾値は保守的に始めて、自分のデータで調整せよ」と繰り返している。「較正済み」とされていても、検証は省略できない。とくに、日本語を含む CJK は英語より精度が落ちると明記されているので、英語以外では confidence をより慎重に扱う必要がある。

### 違い4：運用面

| 観点 | Encoder ＋ 分類ヘッド | Jev |
| --- | --- | --- |
| 実行場所 | 自前ホスト。CPU でも動く | API（`api.typesafe.ai`） |
| ラベルの変更 | 再学習 | リクエストの `criteria` を書き換える |
| 訓練データ | 必要（数百〜数千件） | 不要（ゼロショット） |
| 決定性 | 同一入力なら同一出力 | 「非常に一貫している」とされるが、モデルのバージョンが動けば変わる |
| コンテキスト長 | 512トークン程度が典型 | 64k（state ＋ 全質問）、32k（state ＋ 最長の質問） |
| 料金 | 推論コストのみ | 入力トークン課金（$0.042 / Mtok、出力は無料） |
| 言語 | 学習データ次第 | 英語が主。CJK は精度が落ちる |
| 順序付きラベル | 別途設計 | Score 型で期待値が返る |

## Cross-Encoder としての使い方

[Bi-Encoder / Late Interaction / Cross-Encoder の記事](/blog/ja/bi-late-cross-encoder/)の枠組みでは、Jev の使い方は Cross-Encoder に相当する。クエリと候補を同じ state に入れ、「この候補はクエリに答えているか？」を Noul で問えば、ペアごとのスコアが返る。公式のクックブックは、この方法で BM25の上位30件を再ランキングし、法律文書検索で top-1 精度を5% → 18%、top-10精度を38% → 62%に引き上げている。

ただし、Cross-Encoder と同じくペアごとに評価が必要なので、コーパス全体に対する1段目の検索には向かない。文書側を事前計算する Bi-Encoder や Late Interaction の役割は代替できない。

## 苦手なこと（jaggedness）

TypeSafe は、Jev 1.13 の弱点を「jaggedness（ギザギザ）」という名前で公開している。得意なことと苦手なことの落差が大きい、という意味で使われている。対策に共通するのは「判断はモデルに、それ以外はコードに」という切り分けで、苦手なことの多くはコード側に寄せれば回避できる。以下、4つに分けて見ていく。

### 1. 書かれたとおりにしか読まない

Jev は instructions に書かれた言葉をそのまま解釈し、書かれていない意図は汲まない。「重大なバグか？」とだけ聞いて「重大」の定義を書かなければ、人なら文脈から補うところを Jev は補わない。否定形や二重否定、「A の担当者の上司は承認権限を持つか」のように state の中を何段もたどる質問でも、精度が落ちる。

**対策:** 条件は instructions と criteria にすべて書く。間違った答えを見て「本当はこういう意味だった」と説明したくなったら、その説明が instructions に足りなかった部分にあたる。state が JSON なら、見てほしい場所を `ticket.messages[0].text` のようにパスで指定する。

### 2. 数えない・計算しない

Jev は数値を生成できないので、「文字数はいくつか」という質問は投げられない。投げられるのは、「この単語は5文字以上か」（Noul）や「出現回数はどれか」（Choice で数を選ばせる）のような、数えることを前提にした判断までで、これも当てにならない。日付の前後関係や期間の計算、hex 値で表した色の近さのような数値表現も苦手としている。

**対策:** 数える、比べる、計算するといった処理はコードで行う。たとえば「果物の名前がいくつあるか」なら、要素ごとに「これは果物か？」を Noul で聞き、`True` の数をコードで合計する。日付なら「月は？」「日は？」を Choice で抽出させ、比較はコードで行う。

### 3. state の中身に引きずられる

state に判断と無関係な情報が多いほど、精度が落ちる（context rot）。また、state はデータとして扱われるが、その中に「この問い合わせは billing に分類すべき」と書いてあると、その文に引っ張られることがある。

**対策:** コード側で絞り込んでから渡す。関連する部分だけを state に入れる。絞り込み自体が難しければ、「この段落は質問に関係あるか」を先に Noul で聞いてフィルタする。

### 4. 生成はしない

Jev はテキストを生成しないので、「この文書から日付を抜き出せ」のような自由回答の抽出はできない。Choice を連鎖させて文字列を組み立てることは原理的には可能だが、遅く、精度も出ない。

**対策:** 候補は正規表現や生成モデルで作り、Jev には「どれが正しいか」を Choice で選ばせる。答えの空間が有限なら、抽出は選択問題に変換できる。

## 使い分け

| 状況 | 向いている選択 |
| --- | --- |
| ラベルが固定で、訓練データが数百件以上あり、低レイテンシ・オンプレが必要 | Encoder ＋ 分類ヘッド |
| ラベルが流動的、訓練データがない、複数の判断を同時に取りたい | Jev |
| 順序尺度で「どのあたりか」が欲しい | Jev の Score（Encoder なら順序回帰を別途設計） |
| 較正された確率で閾値運用したい | どちらも可。Encoder は事後較正が前提、Jev も自分のデータで検証は必要 |
| 再ランキング（クエリ・候補ペアのスコア） | どちらも Cross-Encoder 的に使える。Jev はゼロショットで済む |
| 数値計算・日付比較・カウント | どちらでもなく、コード |
| 文章の生成・要約 | どちらでもなく、生成モデル |

Jev は、Transformer Encoder 分類器のインターフェースを3点で拡張したものと捉えると分かりやすい。ラベルを自然言語で与えるゼロショットにしたこと、1つの state に複数の質問を投げられるようにしたこと、較正を学習目標に含めたことの3点になる。
