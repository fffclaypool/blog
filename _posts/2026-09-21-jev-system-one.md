LLM に「この問い合わせは返金依頼か？」と聞くとき、構造化出力を使えば `yes` / `no` のどちらに該当するかと、その「確信度」を申告させることはできる。しかしその確信度は自己申告なので過信気味で当てにならないし、代わりにトークンの logprob を読んでも、生成モデルの確率は語彙全体との競合や表記ゆれで歪んでいる。TypeSafe が公開している **Jev** は、最初から不確かさを確率分布として返すように作られたモデルだ。テキストを生成しない。**状態（state）と型付きの質問（questions）を受け取り、選択肢に対する確率分布と確信度を返す**——それだけをやる。

本記事では、公式ドキュメント（[docs.typesafe.ai](https://docs.typesafe.ai/introduction)）を元に Jev の入出力と学習方針を整理したうえで、同じく「生成しない」モデルである **BERT 系 Transformer Encoder ＋ 分類ヘッド**と何が違うのかを見ていく。なお Jev の内部アーキテクチャ（層数、Encoder か Decoder か、など）は公開されていない。以下の比較は、**公開されているインターフェースと学習目標**に基づくものである。

## Jev とは — System One モデル

TypeSafe は Jev を「最初の **System One モデル**」と呼んでいる。名前は Kahneman の『ファスト＆スロー』に由来し、速く直感的な判断（System 1）を担うモデル、という意味だ。ドキュメントの言葉を借りれば、**「十分な文脈があれば、知識のある人が数秒で下せる種類の判断」**が守備範囲になる。

API はエンドポイント 1 本（`POST /v1/systemone`）で、リクエストは次の 3 要素からなる。

- **`state`**: 評価対象の内容。文字列・JSON オブジェクト・配列のいずれか。テキストのみ（画像・音声は未対応）
- **`questions`**: state に対する質問の集合。各質問は `type`・`instructions`・`criteria` を持つ
- **`model`**: `jev-latest` など

質問は 3 種類に限られる。これを TypeSafe は **AI プリミティブ**と呼ぶ。

| 質問タイプ | 問い | 返り値 |
| --- | --- | --- |
| **Choice** | 選択肢のどれか？ | `choice`, `probabilities`, `confidence` |
| **Score** | 順序付きの段階のどこか？ | `score`, `legend`, `probabilities`, `confidence` |
| **Noul** | この命題は真か？ | `noul`（0〜1 の確率） |

1 リクエストに複数の質問を混ぜて入れられ、**すべての質問は同じ state に対して並列かつ独立に評価される**。質問を増やしてもレスポンス時間はほとんど変わらず、ある質問の答えが別の質問の隠れた文脈になることもない。

## 返ってくるもの — 確率分布と、その要約

具体的なレスポンスを見るのが早い。バグ報告の深刻度を 3 段階で問う Score の例（ドキュメントより）。

```json
{
  "model": "jev-1.13.0",
  "answers": {
    "bug_severity": {
      "type": "score",
      "score": 1.43,
      "confidence": 0.35,
      "legend": {
        "0": "Cosmetic; no impact to functionality",
        "1": "Broken or degraded feature, but workaround exists",
        "2": "Blocking issue; no workaround exists"
      },
      "probabilities": { "0": 0.0, "1": 0.57, "2": 0.43 }
    }
  }
}
```

ここで返り値の意味を数式で押さえておく。$$C$$ 個の選択肢（または段階）に対する確率分布を $$p = (p_0, \ldots, p_{C-1})$$、$$\sum_i p_i = 1$$ とする。

- **Choice** の `choice` は $$\arg\max_i p_i$$、つまり確率が最大の選択肢。
- **Score** の `score` は段階番号の**期待値** $$\sum_{i=0}^{C-1} i \cdot p_i$$。上の例なら $$0 \times 0.0 + 1 \times 0.57 + 2 \times 0.43 = 1.43$$ で、「レベル 1 と 2 の間、やや 1 寄り」という位置を表す。
- **`confidence`** は分布 $$p$$ の尖り具合を $$[0, 1]$$ に潰した統計量。全確率が 1 つの選択肢に乗れば 1.0、一様に近づくほど 0 に近づく。ドキュメントのデモは $$\frac{C \cdot \max_i p_i - 1}{C - 1}$$ で近似しており、公式の厳密な定義は公開されていない。
- **Noul** は「真である確率」そのものを 1 つ返す。0.5 は「yes と no が同確率」であって、「中程度」という意味ではない。

大事なのは、**`confidence` は `probabilities` から導出された二次的な値**だという点だ。閾値で分岐したいだけなら `confidence` を使えばよいが、分布全体が返ってくるので、用途に合わせて別の統計量（エントロピーなど）を自分で計算してもよい、と明記されている。

## 学習方針 — RLHF ではなく RLCD

TypeSafe が最も強調しているのが学習目標の違いだ。事前学習済み言語モデルの後段学習として、彼らは 3 つを並べている。

| 手法 | 目標 | 生み出したもの |
| --- | --- | --- |
| RLHF（Reinforcement Learning from Human Feedback） | 人間が好む応答 | チャットボット |
| RLVR（Reinforcement Learning with Verifiable Rewards） | 検証可能な報酬（数学など） | 推論モデル |
| **RLCD**（Reinforcement Learning for Calibrated Decisions） | **較正された確率での判断** | System One モデル（Jev） |

前の 2 つを簡単に押さえておく。**RLHF** は、モデルの複数の応答に人間が優劣を付け、その好みを報酬モデルとして学習させ、強化学習で「人間に好まれる応答」へ寄せていく手法だ。InstructGPT や ChatGPT を生んだ手法で、ドキュメントによれば TypeSafe の共同創業者 Diogo Almeida はその共同発明者の一人でもある。ただし「人間が好む」が目的なので、自信ありげな断定や迎合（sycophancy）も報酬されやすく、出力分布が特定のスタイルに偏る **mode dropping** も起きる。**RLVR** は、数学の答え合わせやテストの通過のように**機械的に正誤を検証できる報酬**で学習する手法で、o1 系や DeepSeek-R1 に代表される推論モデルを生んだ。正確さは上がるが、長い思考過程を生成するぶん遅く高価になる。

RLCD はどちらとも目的が異なる。人間の好みでも生成した答えの正誤でもなく、**較正された確率を返すこと**そのものを学習目標にする（報酬の具体的な設計は公開されていない）。出力契約は次の 3 点に要約される。①テキストを生成しない、②判断と確率を返す、③**確率が高いほど正解である見込みが実際に高い**。

3 点目が「較正（calibration）」である。確率 0.8 を付けた予測群のうち、実際に約 80% が正解している状態だ。[以前の記事](/blog/ja/classification-confidence/)で見たように、通常のニューラル分類器は系統的に過信し、RLHF を施した LLM はさらに較正が崩れる。TypeSafe の主張は、**較正を後付けの補正ではなく学習目標そのものに据えた**、という点にある。

ただしドキュメント自身が注意しているとおり、較正は**予測群に対する統計的性質**であり、個々の答えの正しさを保証するものではない。「confidence 1.0」は「分布が 1 点に集中している」という意味であって「必ず正しい」という意味ではない。

## Transformer Encoder 分類器との比較

ここからが本題だ。BERT・RoBERTa・DeBERTa などの Encoder に分類ヘッドを載せたモデルも「生成しない」「閉じたラベル集合に対する確率分布を返す」という点で Jev とよく似ている。何が同じで、何が違うのか。

  <figcaption>左：Encoder 分類器はラベル数 C を学習時に固定し、1 系列につき 1 つの分布を返す。右：Jev はラベル集合を自然言語の criteria としてリクエストごとに受け取り、1 state に対する複数の質問を独立に評価する。</figcaption>
</figure>

### 共通点

- 自由文を生成しない。出力は事前に決めた候補集合上の確率分布である
- したがって、Decoder LLM で問題になる「語彙全体との競合」「表記ゆれによる確率の分裂」「複数トークンの長さバイアス」は、少なくともインターフェース上は存在しない
- 確率の argmax がそのまま判断になり、閾値運用・順位付けにそのまま使える

### 違い①: ラベル空間をどこで定義するか

Encoder 分類器では、ラベル集合は**学習時にヘッドの出力次元 $$C$$ として固定**される。ラベルを 1 つ増やしたければヘッドを作り直して再学習が要る。ラベルの意味はデータから暗黙的に学ばれるだけで、モデルは「クラス 2 が何を意味するか」を言葉としては知らない。

Jev では、ラベル集合は**リクエストごとに自然言語の `criteria` として渡す**。Choice なら `{"returns": "Exchanges, wrong or damaged items", ...}`、Score なら段階ごとの説明文の配列だ。同じ重みがすべての利用者・すべてのタスクに使われ、ファインチューニングも LoRA も提供されない。ドメイン知識は `state` と `criteria` の書き方で注入する。

形式的に書けば、Encoder 分類器は $$p = \mathrm{softmax}(W \cdot \mathrm{Enc}(x)_{\mathrm{[CLS]}})$$ で $$W \in \mathbb{R}^{C \times k}$$ が固定なのに対し、Jev は $$p = f(x,\ \text{instructions},\ \text{criteria})$$ という、**ラベルの記述そのものを入力に含む関数**になっている。これはゼロショット分類の形であり、Encoder 系で言えば NLI ベースのゼロショット分類（各ラベルを仮説文にして entailment 確率を取る）に近い発想だ。ただし Jev はそれを単発の NLI ではなく、最初から「候補集合上の較正された分布を返す」タスクとして学習している。

### 違い②: 1 系列 1 タスクか、1 state N 質問か

Encoder 分類器は `[CLS] x [SEP]` を 1 回通して 1 つの分布を返す。3 つの判断が欲しければ、3 つのヘッド（マルチタスク学習）を用意するか、3 回走らせる。

Jev は 1 つの state に対して**任意個の質問を並列・独立に評価する**。ドキュメントはこれを「投機的ファンアウト」と呼び、「必要かもしれない質問は全部投げて、コード側で要るものだけ使え」と推奨している。追加コストは質問ぶんのトークンだけで、レイテンシはほぼ変わらないという。

「独立」であることは Encoder のマルチタスクヘッドと同じに見えるが、Jev の場合は質問の追加・削除が他の質問の答えに影響しないと明記されている点が異なる。Decoder LLM に複数の判断を 1 つのプロンプトで頼むときの「前の答えが後の答えを引きずる」問題（context rot）が、設計上排除されている。

### 違い③: 確率の出どころと較正

Encoder 分類器の確率はロジットの softmax であり、[以前の記事](/blog/ja/classification-confidence/)で整理したとおり、少量データでのファインチューニング後は 0.99 付近に張り付く過信が起きやすく、温度スケーリングなどの**事後較正が実質必須**になる。ただしラベル空間が固定で検証セットも作りやすいので、較正は素直に行える。

Jev は較正を学習目標に含めている（RLCD）ため、**出荷時点で較正されていることを売りにしている**。そして Score 型は、段階の期待値という形で「1.43」のような中間値を返せる。Encoder の名義ラベル分類にはこれに相当する出力がない（順序回帰として別途設計する必要がある）。

一方で、Jev の較正を**自分のデータで検証する手段は Encoder と同じ**だ。検証セットに対して信頼度ダイアグラムを描き、ECE を測る。ドキュメントも「閾値は保守的に始めて、自分のデータで調整せよ」と繰り返している。「較正済み」は出発点であって、検証の省略を意味しない。特に日本語を含む CJK は英語より精度が落ちると明記されており、非英語では confidence をより慎重に扱う必要がある。

### 違い④: 運用面

| 観点 | Encoder ＋ 分類ヘッド | Jev |
| --- | --- | --- |
| 実行場所 | 自前ホスト。CPU でも動く | API（`api.typesafe.ai`） |
| ラベルの変更 | 再学習 | リクエストの `criteria` を書き換える |
| 訓練データ | 必要（数百〜数千件） | 不要（ゼロショット） |
| 決定性 | 同一入力なら同一出力 | 「非常に一貫している」とされるが、モデルのバージョンが動けば変わる |
| コンテキスト長 | 512 トークン程度が典型 | 64k（state ＋ 全質問）、32k（state ＋ 最長の質問） |
| 料金 | 推論コストのみ | 入力トークン課金（$0.042 / Mtok、出力は無料） |
| 言語 | 学習データ次第 | 英語が主。CJK は精度が落ちる |
| 順序付きラベル | 別途設計 | Score 型で期待値が返る |

## Cross-Encoder としての使い方

[Bi-Encoder / Late Interaction / Cross-Encoder の記事](/blog/ja/bi-late-cross-encoder/)で整理した枠組みで言えば、Jev の使われ方は **Cross-Encoder** に相当する。クエリと候補を同じ state に入れ、「この候補はクエリに答えているか？」を Noul で問えば、ペアごとのスコアが返る。公式のクックブックはまさにこの形で BM25 の上位 30 件を再ランキングし、法律文書検索で top-1 精度を 5% → 18%、top-10 精度を 38% → 62% に引き上げている。

ただし Cross-Encoder と同様、ペアごとにフル評価が必要なので、コーパス全体に対する一段目の検索には向かない。文書側を事前計算する Bi-Encoder / Late Interaction の役割は代替できない。

## 苦手なこと — jaggedness

TypeSafe は Jev 1.13 の弱点を「jaggedness（ギザギザ）」という名前で公開している。得意なことと苦手なことの落差が大きい、という意味だ。共通するのは「**判断はモデルに、それ以外はコードに**」という切り分けで、苦手なことの多くはコード側に寄せれば回避できる。大きく 4 つに分けて見ていく。

### ① 書かれたとおりにしか読まない

Jev は instructions に書かれた言葉をそのまま解釈し、書かれていない意図は汲まない。「重大なバグか？」とだけ聞いて「重大」の定義を書かなければ、人なら文脈から補うところを Jev は補わない。否定形や二重否定、「A の担当者の上司は承認権限を持つか」のように state の中を何段もたどる質問も精度が落ちる。

**対策:** 条件は instructions と criteria に書き切る。間違った答えを見て「本当はこういう意味だった」と説明したくなったら、その説明が instructions に足りなかった部分だ。state が JSON なら、見てほしい場所を `ticket.messages[0].text` のようにパスで名指しする。

### ② 数えない・計算しない

Jev は数値を生成できないので、そもそも「文字数はいくつか」という質問は投げられない。投げられるのは「この単語は 5 文字以上か」（Noul）や「出現回数はどれか」（Choice で数を選ばせる）のように、数えることを前提にした判断までだが、これも当てにならない。日付の前後関係や期間の計算、hex 値で表した色の近さのような数値表現も同様に苦手だ。

**対策:** 数える・比べる・計算するはコードでやる。たとえば「果物の名前がいくつあるか」なら、要素ごとに「これは果物か？」を Noul で聞き、`True` の数をコードで合計する。日付なら「月は？」「日は？」を Choice で抽出だけさせ、比較はコードに任せる。

### ③ state の中身に引きずられる

state に判断と無関係な情報が多いほど精度が落ちる（context rot）。また state はあくまでデータとして扱われるが、その中に「この問い合わせは billing に分類すべき」と書いてあれば、その文章に引っ張られることがある。

**対策:** コード側で絞り込んでから渡す。関連する部分だけを state に入れ、絞り込み自体が難しければ「この段落は質問に関係あるか」を Noul で先に聞いてフィルタする。

### ④ 生成はしない

Jev はテキストを生成しないので、「この文書から日付を抜き出せ」のような自由回答の抽出はできない。Choice を連鎖させて無理やり文字列を組み立てることは原理的に可能だが、遅く精度も出ない。

**対策:** 候補は正規表現や生成モデルで作り、Jev には「どれが正しいか」を Choice で選ばせる。答えの空間が有限なら、抽出は選択問題に変換できる。

## 使い分け

| 状況 | 向いている選択 |
| --- | --- |
| ラベルが固定で、訓練データが数百件以上あり、低レイテンシ・オンプレが必要 | Encoder ＋ 分類ヘッド |
| ラベルが流動的、訓練データがない、複数の判断を同時に取りたい | Jev |
| 順序尺度で「どのあたりか」が欲しい | Jev の Score（Encoder なら順序回帰を別途設計） |
| 較正された確率で閾値運用したい | どちらも可。Encoder は事後較正が前提、Jev も自分のデータで検証は必要 |
| 再ランキング（クエリ・候補ペアのスコア） | どちらも Cross-Encoder 的に使える。Jev はゼロショットで済む |
| 数値計算・日付比較・カウント | どちらでもなく、コード |
| 文章の生成・要約 | どちらでもなく、生成モデル |

まとめると——Jev は「Transformer Encoder 分類器のインターフェース」を「ラベルを自然言語で与えるゼロショット」「1 state N 質問」「較正を学習目標に含める」の 3 点で拡張したもの、と捉えるのが分かりやすい。
